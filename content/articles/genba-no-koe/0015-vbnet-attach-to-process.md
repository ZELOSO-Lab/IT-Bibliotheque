# 【VB.NET】F5では再現しないバグを「プロセスにアタッチ」で捕まえる手順と、ブレークポイントが止まらない7つの原因

## 現場の声

> 「メニューから受注画面を開いて、得意先を選び直すと金額がゼロになります」
>
> 受注画面の .exe は、ランチャー（メニュー画面）から**起動引数とログイン情報を渡されて**起動する作りでした。Visual Studio で F5 を押して受注画面だけを起動すると、引数がないのでログインエラー。仕方なく引数を手で設定して起動すると、今度は**現象が再現しない**。
>
> そこで MessageBox を何か所にも仕込んでビルドし、exe を差し替えて試す作業を半日繰り返しました。先輩に相談すると、「メニューから普通に起動して、VS からアタッチすればいいよ」とのこと。Ctrl+Alt+P でプロセスを選んでアタッチすると、**いつもの起動方法のまま**ブレークポイントで止まり、変数の値を確認できました。原因は、ランチャーから渡される得意先コードの桁数が、手で設定した値と違っていたことでした。

「プロセスにアタッチ」は、**すでに動いているアプリにあとからデバッガーをつなぐ**機能です。F5 と同じように、ブレークポイント・ステップ実行・変数の確認ができます。この記事では、アタッチの基本手順と、「つないだのに止まらない」ときの原因を順番に整理します。

## 前提の構成

よくある構成を例にします。

```text
C:\src\Sales\
├─ Sales.sln
├─ Launcher\        ← メニュー画面（Launcher.exe）。各業務画面の exe を起動する
└─ OrderEntry\      ← 受注画面（OrderEntry.exe）。今回デバッグしたいアプリ
    └─ bin\Debug\
        ├─ OrderEntry.exe
        └─ OrderEntry.pdb   ← デバッグ情報（シンボル）。アタッチではこれが重要

ランチャー → OrderEntry.exe /user:U001 /tokui:000123 のように引数を渡して起動
```

- 対象は .NET Framework 4.x の Windows Forms（VB.NET）、Visual Studio 2019 / 2022 です。.NET 6 以降の場合の違いは本文中で補足します。
- メニューの表記は日本語版 Visual Studio のものです。

## F5 とアタッチの違い

| | F5（デバッグ開始） | プロセスにアタッチ |
| --- | --- | --- |
| 起動するのは | Visual Studio | ランチャー・タスクスケジューラ・利用者など、いつもの起動元 |
| 起動引数・作業フォルダ | プロジェクトの設定値 | 実際の起動元が渡した値 |
| つなぐタイミング | 起動した瞬間から | アタッチした瞬間から（それより前の処理は追えない） |
| 終了の仕方 | 停止するとアプリも終了 | 「すべてデタッチ」でアプリを動かしたまま切り離せる |

**「いつもの起動方法でしか再現しない」**ときは、アタッチを使うのが一番早い方法です。

## 基本手順：5分でアタッチする

1. デバッグしたい exe を**Debug 構成でビルド**し、exe と同じフォルダに `.pdb` があることを確認する
2. ランチャーなど、いつもの方法でアプリを起動する
3. Visual Studio で同じソリューションを開き、デバッグしたい行にブレークポイントを置く（F9）
4. メニュー「デバッグ」→「プロセスにアタッチ」（**Ctrl+Alt+P**）
5. 「プロセスのフィルター」に `OrderEntry` と入力し、一覧に出た `OrderEntry.exe` を選ぶ
6. 「アタッチ先」が「自動」で、マネージドコードが選ばれていることを確認して「アタッチ」
7. アプリを操作すると、ブレークポイントで止まる

止まったあとの操作は F5 のときと同じです。F10（ステップオーバー）、F11（ステップイン）、ローカルウィンドウやウォッチで変数を確認できます。

調査が終わったら「デバッグ」→「**すべてデタッチ**」を選びます。アプリは終了せず、そのまま使い続けられます。

> 2回目以降は「デバッグ」→「プロセスに再アタッチ」（**Shift+Alt+P**）で、前回と同じ名前のプロセスに一発でアタッチできます。修正→ビルド→起動→アタッチを繰り返すときに便利です。

## ハマりどころ1：ブレークポイントが白抜きの丸になり、止まらない

アタッチした直後に、ブレークポイントの赤丸が**白抜き**になり、マウスを合わせると次のように表示されることがあります。

```text
現在、ブレークポイントにヒットしません。このドキュメントのシンボルは読み込まれていません。
```

**原因：アタッチした exe に対応する `.pdb`（シンボル）が読み込まれていない。**

デバッガーは `.pdb` を使って「exe のこの命令は、ソースのこの行」という対応を取ります。exe だけをどこかにコピーして起動していると、`.pdb` が見つからず止まりません。

**対処：**

1. アタッチ中に「デバッグ」→「ウィンドウ」→「モジュール」（**Ctrl+Alt+U**）を開く
2. `OrderEntry.exe` の行の「シンボルの状態」と「パス」を見る
   - 「シンボルが読み込まれていません」→ exe と同じフォルダに、**同じビルドで作られた** `.pdb` を置く
   - 「パス」が想定外のフォルダ → 別の場所の exe にアタッチしている（ハマりどころ2へ）
3. 行を右クリック →「シンボルの読み込み」で、`.pdb` の場所を手で指定することもできます

## ハマりどころ2：止まった行がずれている／「ソースファイルが元のバージョンと異なります」

ブレークポイントにマウスを合わせると次のように表示される、または止まった位置がおかしい場合です。

```text
ブレークポイントにはヒットしません。ソース ファイルが元のバージョンと異なります。
```

**原因：アタッチした exe が、今開いているソースより古い（または新しい）ビルド。**

よくあるのは次のパターンです。

- ランチャーが `bin\Debug` ではなく、**配置用フォルダ（例：`C:\Sales\bin`）にコピーされた古い exe** を起動している
- ソースを修正したが、ビルドしただけで配置用フォルダにコピーしていない

**対処：** モジュールウィンドウの「パス」で、実際に動いている exe の場所を確認します。そのうえで、次のどちらかにそろえます。

- ランチャーの起動先を `bin\Debug` の exe に向ける
- ビルド後に exe と `.pdb` を**セットで**配置用フォルダへコピーする

「この場所で止まってほしい」という目的で、ブレークポイントの設定から「ソース コードが元のバージョンと完全に一致する必要がある」を外すこともできます。ただし、行がずれた状態で値を見ても判断を誤るので、基本はビルドをそろえてください。

## ハマりどころ3：「アタッチ先」が違うコードの種類になっている

アタッチは成功しているのに、ブレークポイントが全部白抜きのまま、という場合です。

**原因：デバッガーの種類（アタッチ先）が、アプリと合っていない。**

「アタッチ先」が「自動」でも、ネイティブ DLL を多く読み込むアプリでは、意図しない種類が選ばれることがあります。

**対処：** 「アタッチ先」の「選択」を押し、「次のコードの種類をデバッグする」で明示的に選びます。

| アプリ | 選ぶもの |
| --- | --- |
| .NET Framework 4.x の VB.NET | マネージド (.NET Framework 4.x) |
| .NET 6 以降の VB.NET | マネージド (.NET Core, .NET 5+) |
| C/C++ の DLL の中も追いたい | 上に加えて「ネイティブ」 |

選んだ種類は次回以降も保持されるので、一度設定すれば済みます。

## ハマりどころ4：一覧にプロセスが出ない／「アクセスが拒否されました」

**原因：アプリが別ユーザーや管理者権限で動いている。**

- Windows サービスや、タスクスケジューラから別ユーザーで起動したバッチ
- 「管理者として実行」で起動したアプリ

**対処：**

- 「プロセスにアタッチ」画面の「**すべてのユーザーからのプロセスを表示する**」にチェックを入れる
- Visual Studio 自体を「**管理者として実行**」で起動し直す

アプリ側の権限が Visual Studio より高いと、一覧に出てもアタッチできません。Visual Studio の権限を、アプリと同じかそれ以上にそろえてください。

## ハマりどころ5：起動直後の処理（Form_Load など）にアタッチが間に合わない

アタッチは「つないだ瞬間から」しか追えません。起動直後に実行される `Sub Main`・`Form_Load`・ランチャーから受け取った引数の解析などは、手でアタッチしている間に終わってしまいます。

**対処：起動時にデバッガーを待つ仕組みを、Debug ビルドにだけ入れておく。**

```vb
Imports System.Diagnostics

Module Program
    <STAThread>
    Sub Main()
#If DEBUG Then
        ' 環境変数 ORDER_WAIT_DEBUGGER=1 のときだけ、アタッチされるまで待つ
        If Environment.GetEnvironmentVariable("ORDER_WAIT_DEBUGGER") = "1" Then
            Do Until Debugger.IsAttached
                Threading.Thread.Sleep(500)
            Loop
            Debugger.Break()   ' アタッチされたらここで一時停止
        End If
#End If
        Application.EnableVisualStyles()
        Application.SetCompatibleTextRenderingDefault(False)
        Application.Run(New OrderEntryForm())
    End Sub
End Module
```

使い方は次のとおりです。

1. コマンドプロンプトで `set ORDER_WAIT_DEBUGGER=1` を実行し、そこからランチャーを起動する（子プロセスに環境変数が引き継がれます）
2. 受注画面を開くと、画面が出ないまま待機する
3. Visual Studio から `OrderEntry.exe` にアタッチすると、`Debugger.Break()` で止まる
4. あとは F10 / F11 で起動処理を追える

ポイントは次の3つです。

- `#If DEBUG Then` で囲むので、**Release ビルドには入りません**。本番で待ち続ける事故を防げます。
- 環境変数で切り替えるので、普段の開発では待ちません。
- `Debugger.Launch()` を使うと「どのデバッガーで開くか」のダイアログが出せますが、環境によってはダイアログが出ないことがあります。上の「待つ」方式は、どの環境でも同じように動きます。

> プロジェクトのプロパティで「アプリケーション フレームワークを有効にする」にチェックが入っていて `Sub Main` がない場合は、`ApplicationEvents.vb` の `MyApplication_Startup` イベントに同じ処理を書きます。

## ハマりどころ6：変数が「最適化されているため、値を評価できません」

Release ビルドの exe にアタッチすると、ローカル変数の値が見られず、ステップ実行も飛び飛びになります。

```text
最適化されているため、式の値を評価できません。
```

**原因：コンパイラーと JIT が最適化をかけて、変数や行の対応を消している。**

**対処：**

- 基本は **Debug 構成でビルドした exe** にアタッチする
- どうしても Release の exe で調べたい場合は、「ツール」→「オプション」→「デバッグ」→「全般」の「**モジュールの読み込み時に JIT 最適化を抑制する (マネージドのみ)**」にチェックを入れます。この設定は**デバッガーがつながったあとに読み込まれたモジュール**にしか効きません。起動済みのアプリにあとからアタッチしても exe 本体には効かないので、ハマりどころ5の「待つ」方式と組み合わせるか、F5 で起動して使います

あわせて、Release 構成でも `.pdb` を出力する設定（プロジェクトのプロパティ →「コンパイル」→「詳細コンパイル オプション」→「デバッグ情報の生成」を「pdb-only」など）にしておくと、あとから調べやすくなります。

## ハマりどころ7：Try-Catch で例外が握りつぶされて、どこで起きたか分からない

既存コードによくある書き方です。

```vb
Try
    lblAmount.Text = CalcAmount(tokuiCode).ToString("#,0")
Catch ex As Exception
    lblAmount.Text = "0"   ' 例外を握りつぶして 0 を表示
End Try
```

アタッチしても、例外は Catch で処理されているので**どこでも止まりません**。画面上は「金額がゼロ」になるだけです。冒頭の事故も、実はこのパターンでした。

**対処：例外が「スローされた瞬間」に止まるように設定する。**

1. 「デバッグ」→「ウィンドウ」→「例外設定」（**Ctrl+Alt+E**）
2. 「**Common Language Runtime Exceptions**」にチェックを入れる
3. 操作をやり直すと、Catch に入る前の、**例外が発生した行**で止まる

全部の例外で止まると多すぎる場合は、「Common Language Runtime Exceptions」を展開して、`System.InvalidCastException` や `System.FormatException` など、疑わしい例外だけにチェックを入れます。

## 番外：ブレークで止めている間、アプリは完全に止まっている

ブレークポイントで止まっている間、アプリの画面は**応答なし**になります。

- タイマー処理やソケット通信は、止めている間にタイムアウトすることがある
- 共有の検証環境で他の人が使っている画面にアタッチすると、その人の画面も止まる

調べ終わったら、F5 で再開するか「すべてデタッチ」で切り離します。共有環境では、アタッチする前に一声かけてください。

## 調査手順（まとめ）

### 1. 準備する

- Debug 構成でビルドし、exe と `.pdb` をセットで、起動元が参照する場所に置く
- 起動直後の処理を追うなら、ハマりどころ5の「デバッガーを待つ」処理を入れておく

### 2. いつもの方法で起動する

- ランチャー・タスクスケジューラなど、現象が出る起動方法で起動する

### 3. アタッチする

- Ctrl+Alt+P → フィルターに exe 名 → アタッチ先を確認 → アタッチ
- 2回目以降は Shift+Alt+P

### 4. つながったか確認する

- ブレークポイントが赤丸（塗りつぶし）になっているか
- 白抜きならモジュールウィンドウ（Ctrl+Alt+U）で、パスとシンボルの状態を確認する

### 5. 原因を追う

- 怪しい行にブレークポイント → 操作 → 変数を確認
- 値がゼロ・空になるだけでエラーが出ないなら、例外設定（Ctrl+Alt+E）で CLR 例外にチェック

### 6. 切り離す

- 「すべてデタッチ」でアプリを動かしたまま終了する

### 補足：別の PC で動いているアプリにアタッチする場合

検証機など、別の PC で動いているアプリにもアタッチできます。相手の PC で**リモート デバッガー（msvsmon.exe）**を起動し、「プロセスにアタッチ」画面の「接続ターゲット」に相手の PC 名を入れます。リモート デバッガーは Visual Studio のバージョンに合ったものを、Microsoft の公式サイトから入手してください。本番環境へのアタッチは業務を止めるので、原則として行わず、検証環境で再現させてから使います。

## チェックリスト

- [ ] アタッチする exe は Debug 構成でビルドしたものか
- [ ] exe と同じフォルダに、同じビルドの `.pdb` があるか
- [ ] ランチャーが起動している exe の場所を、モジュールウィンドウで確認したか
- [ ] 「アタッチ先」のコードの種類が、.NET Framework / .NET 6 以降と合っているか
- [ ] サービスや管理者権限のアプリには、Visual Studio も管理者で起動してアタッチしたか
- [ ] 起動直後の処理は、Debug ビルド限定の「デバッガーを待つ」処理で止めたか
- [ ] 例外が握りつぶされていそうな場合、例外設定で CLR 例外にチェックを入れたか
- [ ] 調査後は「すべてデタッチ」で切り離したか
- [ ] 「デバッガーを待つ」処理が `#If DEBUG Then` の中にあり、Release に入らないことを確認したか

## まとめ

- 「いつもの起動方法でしか再現しない」バグは、F5 で再現させようとせず、**動いているアプリにアタッチ**するのが近道です。
- 手順は Ctrl+Alt+P → exe を選ぶ → アタッチの3ステップ。2回目以降は Shift+Alt+P です。
- 止まらないときは、まず**モジュールウィンドウ（Ctrl+Alt+U）で exe のパスと `.pdb` の状態**を見ます。原因の多くは「古い exe」か「`.pdb` がない」のどちらかです。
- 起動直後の処理は「デバッガーを待つ」処理、握りつぶされた例外は「例外設定」で捕まえます。

C言語のプログラムを gdb でアタッチする方法は、「【C言語】gdbで「どこで・なぜ落ちたか」を10分で突き止める手順」の記事で紹介しています。
