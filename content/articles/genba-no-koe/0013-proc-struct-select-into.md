# 【C言語】SELECT結果を構造体にINTOしたらエラー。原因は「型の不一致」、DB設計書＋VLOOKUP＋サクラエディタで構造体を作り直した手順（Pro*C）

## 現場の声

> C言語（Pro*C）で、SELECT した1行を構造体型の変数にまとめて INTO したところ、実行時にエラーになりました。
>
> 原因は、**SELECT の結果（テーブルの列の型・桁数）と、構造体メンバの型・サイズが合っていなかった**ことです。構造体は昔のソースからコピーしたもので、テーブル定義が変わったあと誰も直していませんでした。
>
> 列は数十個あり、1つずつ設計書と見比べて手で直すのは現実的ではありません。そこで、
>
> - DB設計書を開く
> - Excel の VLOOKUP で、列ごとの型とサイズを取得する
> - サクラエディタの置換で、構造体の宣言の形に整える
> - 構造体はヘッダーファイルに追加する
>
> という流れで、短時間で正しい構造体に作り直しました。

「構造体に INTO」は、列が多いテーブルを扱う Pro*C では定番の書き方です。そのぶん、**列と構造体のずれ**が一番起きやすい場所でもあります。この記事では、ずれたときに出るエラーとその原因、そして設計書から構造体を機械的に作り直す手順を紹介します。

## 前提の構成

| 項目 | 内容 |
| --- | --- |
| 言語 | C言語（Oracle Pro*C/C++ の埋め込み SQL） |
| DB | Oracle Database |
| 設計書 | Excel のDB設計書（テーブル定義：物理名・型・桁数・小数桁） |
| エディタ | サクラエディタ（正規表現での置換を使用） |

例として、次のテーブルを使います。

| 物理名 | 論理名 | 型 | 桁数 | 小数桁 | NULL |
| --- | --- | --- | --- | --- | --- |
| EMP_NO | 社員番号 | VARCHAR2 | 10 | | NOT NULL |
| EMP_NAME | 氏名 | VARCHAR2 | 40 | | |
| DEPT_CD | 部署コード | CHAR | 4 | | |
| SALARY | 月給 | NUMBER | 9 | 0 | |
| RATE | 評価係数 | NUMBER | 5 | 2 | |
| TOTAL_AMT | 累計支給額 | NUMBER | 12 | 0 | |
| HIRE_DATE | 入社日 | DATE | | | |

エラーになった「直す前」の構造体とSQLは次のとおりです。

```c
typedef struct {
    char   emp_no[8];      /* 設計書は VARCHAR2(10)。桁が足りない */
    char   emp_name[40];   /* 終端の '\0' の分が足りない */
    char   dept_cd[4];     /* 同上 */
    short  salary;         /* NUMBER(9) は short に入りきらない */
    int    rate;           /* NUMBER(5,2) の小数が消える */
    int    total_amt;      /* NUMBER(12) は int に入りきらない */
    char   hire_date[8];   /* DATE を文字で受けるには短い */
} EMP_REC;

EMP_REC emp;

EXEC SQL SELECT emp_no, emp_name, dept_cd, salary, rate, total_amt, hire_date
           INTO :emp
           FROM employee
          WHERE emp_no = :key_emp_no;
```

## まず結論：構造体INTOは「順番・型・サイズ」が列と一致している必要がある

Pro*C で構造体を INTO に指定すると、**SELECT 句の1列目が構造体の1番目のメンバへ、2列目が2番目へ**と、宣言の順番どおりに入ります。名前では対応づけられません。

そのため、次の3つのどれかがずれるとエラーや値化けが起きます。

| ずれ | 起きること |
| --- | --- |
| 順番・個数 | 別の列の値が入る、ORA-01007（選択リストにない変数）など |
| サイズ（文字列） | ORA-01406（列の値が切り捨てられた） |
| 型（数値） | ORA-01455（整数型に変換するとオーバーフロー）、小数が黙って消える |

エラーメッセージは Oracle やプリコンパイラのバージョン、オプションによって異なる場合があります。メッセージが違っても、**まず列定義と構造体を並べて比較する**のが一番の近道です。

## ハマりどころ1：文字列の配列が「桁数ちょうど」で、終端の分が足りない

**症状**

ORA-01406（フェッチした列の値が切り捨てられた）が出る。値の末尾が欠ける。

**原因**

Pro*C の既定（`CHAR_MAP=CHARZ`）では、`char` 配列のホスト変数に**終端の `'\0'` が付きます**。`VARCHAR2(40)` を `char emp_name[40]` で受けると、40桁のデータが入りきりません。

**対処**

文字列の列は **「桁数 + 1」** の配列にします。`[40 + 1]` のように書いておくと、「+1 は終端の分」だと誰が見ても分かります（定数式なので C として正しい書き方です）。

```c
char emp_name[40 + 1];   /* VARCHAR2(40) + 終端 */
char dept_cd[4 + 1];     /* CHAR(4) + 終端 */
```

## ハマりどころ2：文字コードがUTF-8で、日本語が「桁数 + 1」でも入らない

**症状**

英数字だけのデータは問題ないのに、日本語を含む行だけ ORA-01406 になる。

**原因**

`VARCHAR2(40 CHAR)` のように**文字数**で定義された列は、DB の文字コードが AL32UTF8 だと最大で 40 × 3〜4 バイトになります。C の `char` 配列は**バイト数**です。

**対処**

設計書の桁数が「バイト」か「文字」かを確認します。文字数定義なら、クライアントの文字コードでの最大バイト数を確保します。

```c
char emp_name[40 * 3 + 1];   /* 40文字（UTF-8で最大3バイト/文字と想定）+ 終端 */
```

## ハマりどころ3：NUMBER を short / int で受けて、桁があふれる

**症状**

ORA-01455（列の変換で整数データ型がオーバーフローした）が出る。大きい金額の行だけ失敗する。

**原因**

`short` は約3万、`int`（32ビット）は約21億までしか入りません。`NUMBER(9)` は最大 999,999,999 なので `short` では足りず、`NUMBER(12)` は `int` に入りきりません。

**対処**

桁数で型を決めます。この記事では次のルールにしました。

| 列の型 | 構造体メンバの型 |
| --- | --- |
| NUMBER(1〜9) で小数なし | `int` |
| NUMBER(10以上) または 小数あり | `double` |
| 金額などで1円の誤差も許されない、15桁を超える | 文字列で受けて変換する（`char [桁数 + 3]` など） |

`long` は Windows（64ビットでも32ビット）と Linux（64ビット）でサイズが違うため、桁あふれ対策として使うのは避けています。

## ハマりどころ4：小数のある NUMBER を int で受けて、小数が黙って消える

**症状**

エラーは出ないのに、`RATE` が 1.25 ではなく 1 になっている。

**原因**

`NUMBER(5,2)` を `int` で受けると、小数部分が切り捨てられます。**エラーにならないため、一番気づきにくい**ずれです。

**対処**

小数桁が 0 以外の列は `double` で受けます。設計書の「小数桁」列を必ず確認します。

## ハマりどころ5：DATE をそのまま文字配列で受けて、形式が変わる・切り捨てられる

**症状**

日付が `13-OCT-26` のような形式で入る。環境によって形式が違う。ORA-01406 になる。

**原因**

DATE を文字で受けると、**セッションの `NLS_DATE_FORMAT`** の形式に変換されます。環境ごとに形式も長さも変わります。

**対処**

SELECT で `TO_CHAR` を使い、形式を固定します。構造体はその長さ + 1 にします。

```sql
TO_CHAR(hire_date, 'YYYYMMDDHH24MISS')   -- 14桁で固定
```

```c
char hire_date[14 + 1];
```

## ハマりどころ6：NULL の列で ORA-01405 になる

**症状**

型もサイズも合わせたのに、一部の行で ORA-01405（フェッチした列の値が NULL）が出る。

**原因**

標識変数（インジケータ）を指定していないと、NULL を受け取れずにエラーになります（`UNSAFE_NULL=YES` などのオプション設定による）。

**対処**

構造体と同じ並びの**標識変数の構造体**を用意し、`:emp:emp_ind` のように指定します。標識変数が -1 なら NULL です。

```c
typedef struct {
    short emp_no;
    short emp_name;
    /* …構造体 EMP_REC と同じ順番・同じ個数で short を並べる… */
} EMP_REC_IND;
```

```c
EXEC SQL SELECT ... INTO :emp:emp_ind FROM employee WHERE ...;
```

## ハマりどころ7：SELECT の列の並びと構造体の並びがずれる

**症状**

エラーは出ないが、`dept_cd` に氏名の一部が入っている。列を追加したあとから値がおかしい。

**原因**

構造体 INTO は**順番で対応**します。`SELECT *` を使っていたり、テーブルに列を追加したときに SELECT 句か構造体の片方だけを直したりすると、1つずつずれます。

**対処**

- `SELECT *` は使わず、**列名を構造体と同じ順番で明示**する
- 構造体の各メンバに、対応する列名と型をコメントで残す
- 設計書の列順から構造体と SELECT 句を**同じ手順で一緒に作る**（次の章）

## 修正手順：DB設計書 → VLOOKUP → サクラエディタ → ヘッダーファイル

列が多いテーブルでも、**手で1行ずつ直さず、設計書から機械的に作る**のが早く、間違いもありません。

### 手順1：DB設計書を開き、テーブル定義シートを確認する

設計書のテーブル定義シート（例：シート名 `EMPLOYEE`）で、次の列の位置を確認します。

| 列 | 内容 |
| --- | --- |
| B | 物理名 |
| C | 論理名 |
| D | 型 |
| E | 桁数 |
| F | 小数桁 |

設計書が最新版かどうか（改訂履歴・更新日）も、ここで必ず確認します。古い設計書から作ると、同じずれをもう一度作ることになります。

### 手順2：VLOOKUP で、SELECT の列順に型と桁数を取得する

新しいシート（例：`作業`）の A 列に、**SELECT 句の列順で物理名**を並べます。B〜D 列で、設計書から型・桁数・小数桁を引きます。

| | A（物理名） | B（型） | C（桁数） | D（小数桁） |
| --- | --- | --- | --- | --- |
| 1 | EMP_NO | `=VLOOKUP($A1,EMPLOYEE!$B:$F,3,FALSE)` | `=VLOOKUP($A1,EMPLOYEE!$B:$F,4,FALSE)&""` | `=VLOOKUP($A1,EMPLOYEE!$B:$F,5,FALSE)&""` |
| 2 | EMP_NAME | （下へコピー） | （下へコピー） | （下へコピー） |

ポイントは次のとおりです。

- 第4引数は必ず **`FALSE`（完全一致）**。省略すると近い値が返り、別の列の型を拾います
- 範囲は **`$B:$F` のように絶対参照**にして、下へコピーしてもずれないようにする
- `&""` を付けると、桁数が空欄の列（DATE など）が `0` ではなく空欄になります
- `#N/A` が出た行は、列名の綴り違いか、設計書に載っていない列です。**ここで見つかる不一致が、そもそものバグの原因**であることも多いです
- Microsoft 365 なら `XLOOKUP` でも同じことができます

結果は次のようになります。

```text
EMP_NO     VARCHAR2  10
EMP_NAME   VARCHAR2  40
DEPT_CD    CHAR      4
SALARY     NUMBER    9   0
RATE       NUMBER    5   2
TOTAL_AMT  NUMBER    12  0
HIRE_DATE  DATE
```

### 手順3：サクラエディタに貼り付けて、構造体の形に整える

A〜D 列をコピーしてサクラエディタに貼り付けます。Excel からコピーすると、**列の区切りはタブ**になります。

1. **全体を小文字にする**：Ctrl+A で全選択 → 「変換 → 英大文字→英小文字」（既定のキー割り当てでは Ctrl+U）
2. **Ctrl+R で置換ダイアログを開き、「正規表現」にチェック**を入れて、次の4つを上から順に「すべて置換」する

| 順 | 置換前（正規表現） | 置換後 | 対象 |
| --- | --- | --- | --- |
| 1 | `^(\w+)\t(?:varchar2\|char)\t(\d+)\t\d*$` | `    char    $1[$2 + 1];` | 文字列 |
| 2 | `^(\w+)\tnumber\t[1-9]\t0?$` | `    int     $1;` | 9桁以下の整数 |
| 3 | `^(\w+)\tnumber\t\d+\t\d*$` | `    double  $1;` | 残りの NUMBER |
| 4 | `^(\w+)\tdate\t\t$` | `    char    $1[14 + 1];` | 日付 |

結果は次のとおりです。

```c
    char    emp_no[10 + 1];
    char    emp_name[40 + 1];
    char    dept_cd[4 + 1];
    int     salary;
    double  rate;
    double  total_amt;
    char    hire_date[14 + 1];
```

置換されずに残った行は、**ルールに当てはまらない型**（桁数指定のない NUMBER、CLOB など）です。その行だけ手で判断します。

あわせて、SELECT 句も同じ列一覧から作ると、順番のずれが起きません。手順2の A 列だけをサクラエディタに貼り、行末に `,` を付けます（置換前 `$`、置換後 `,`）。最終行の `,` を消し、DATE の列だけ `TO_CHAR` に書き換えれば完成です。

サクラエディタの置換・矩形選択の使い方は、「サクラエディタ」の記事で詳しく扱っています。

### 手順4：構造体をヘッダーファイルに追加する

整えた宣言を、構造体用のヘッダーファイルに追加します。複数の `.pc` から使う構造体は、ヘッダーにまとめておくと、次にテーブルが変わったときも1か所の修正で済みます。

```c
/* emp_rec.h : EMPLOYEE テーブル 1行分（DB設計書 v1.3 から作成） */
#ifndef EMP_REC_H
#define EMP_REC_H

typedef struct {
    char    emp_no[10 + 1];     /* EMP_NO     VARCHAR2(10) */
    char    emp_name[40 + 1];   /* EMP_NAME   VARCHAR2(40) */
    char    dept_cd[4 + 1];     /* DEPT_CD    CHAR(4)      */
    int     salary;             /* SALARY     NUMBER(9)    */
    double  rate;               /* RATE       NUMBER(5,2)  */
    double  total_amt;          /* TOTAL_AMT  NUMBER(12)   */
    char    hire_date[14 + 1];  /* HIRE_DATE  DATE → TO_CHAR 'YYYYMMDDHH24MISS' */
} EMP_REC;

#endif /* EMP_REC_H */
```

`.pc` 側でインクルードし、SELECT 句を構造体と同じ順番にします。

```c
#include "emp_rec.h"

EMP_REC emp;

EXEC SQL SELECT emp_no, emp_name, dept_cd, salary, rate, total_amt,
                TO_CHAR(hire_date, 'YYYYMMDDHH24MISS')
           INTO :emp
           FROM employee
          WHERE emp_no = :key_emp_no;
```

**注意：プリコンパイラにもヘッダーを見せる**

ホスト変数の型は、C コンパイラだけでなく **Pro*C のプリコンパイラ**も知っている必要があります。ヘッダーを別フォルダに置いた場合は、`proc` の `INCLUDE=` オプションにそのフォルダを追加します。プリコンパイルで「未定義の識別子」のようなエラーが出たら、まずここを確認します。

```text
proc iname=emp_select.pc include=../include
```

### 手順5：プリコンパイル・ビルドして、境界値で確認する

- 桁数いっぱいの文字列（10桁の社員番号、40桁の氏名）
- 日本語を含む氏名
- 最大値の数値（999,999,999）と小数（1.25）
- NULL を含む行

の4種類のデータで SELECT し、値が欠けずに入ることを確認します。

## チェックリスト

- [ ] 構造体メンバの順番と個数が、SELECT 句の列と一致している
- [ ] `SELECT *` を使っていない
- [ ] 文字列の列は「桁数 + 1」（終端の分）を確保している
- [ ] 桁数が「バイト」か「文字」かを確認し、UTF-8 の日本語でも入るサイズにしている
- [ ] NUMBER の桁数で `int` / `double` / 文字列を選んでいる（`short` / `long` を安易に使っていない）
- [ ] 小数のある列を整数型で受けていない
- [ ] DATE は `TO_CHAR` で形式を固定している
- [ ] NULL になりうる列に標識変数を用意している
- [ ] 構造体はヘッダーファイルにまとめ、プリコンパイラの `INCLUDE=` も設定した
- [ ] 最新のDB設計書から作成し、ヘッダーのコメントに版数を残した

## まとめ

- 構造体への INTO は、**列と構造体の「順番・型・サイズ」が一致している**ことが前提です。どれか1つでもずれると、ORA-01406 / ORA-01455 などのエラーや、黙って値が変わるバグになります。
- 列が多いときは、**DB設計書 → VLOOKUP で型・桁数を取得 → サクラエディタの正規表現置換で宣言に変換 → ヘッダーファイルに追加**の順で、機械的に作り直すのが早く確実です。
- 同じ列一覧から SELECT 句も作り、ヘッダーに設計書の版数を残しておくと、次にテーブル定義が変わったときも迷わず直せます。

「設計書と見比べて手で直す」をやめるだけで、修正時間も、直し漏れも大きく減ります。
