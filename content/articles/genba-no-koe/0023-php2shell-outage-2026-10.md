# 【障害速報】10/21夜〜22朝、サイトやアプリが一斉に「緊急メンテ」になった原因はPHPの重大脆弱性「php2shell」。利用者がやること・エンジニアがやること

> **最終確認日: 2026年10月22日 12時（日本時間）**
> 状況は動いています。各サービスの再開状況は、必ず公式サイト・公式SNSで確認してください。本文中の「推測」と書いた部分は、公式発表で確認できていない内容です。

## 現場の声

> 「朝起きたら、いつも見ているサイトが開かない。ゲームアプリは『緊急メンテナンス中』。ネットの大規模障害？　自分の回線の問題？」
>
> 調べてみると、止まっていたのは**PHPで動いているWebサービス**でした。回線もクラウドも落ちていません。各社が**自分の判断でサーバーを止めて**、PHPの更新作業をしていたのです。

## 結論（1分で読める版）

- **原因**: PHP（多くのWebサイトを動かしているプログラミング言語）に、**ログイン不要で外部からサーバーを乗っ取れる（RCE）重大な脆弱性が2件**見つかりました。CVE-2026-109618 / CVE-2026-109619、通称 **php2shell**、深刻度は CVSS v4.0 で **9.2（Critical）** です。
- **なぜ一斉に止まったか**: 修正版の公開が**日本時間10月21日23時の予定**と前日に予告され、しかも**修正前から攻撃の試行が観測**されていました。各社は「更新が終わるまで外から触れないようにする」ため、予防的にサービスを止めました。
- **通信障害ではありません**: 回線・DNS・CDN・クラウド全体の障害ではなく、**サービスごとの緊急メンテナンス**です。なので「全部が止まった」わけではなく、PHPを使っているサービスだけが止まっています。
- **利用者がやること**: 基本的には**待つだけ**です。公式発表で再開を確認し、念のためパスワードの使い回しをやめておきましょう。
- **エンジニアがやること**: PHPを **8.5.12 / 8.4.27 / 8.3.36 / 8.2.35 以上**へ更新し、**PHPのワーカーを再起動**します。**8.1以前は公式の修正がありません**。

## なぜ「一斉に」止まったのか

### 1. PHPは「Webの土台」だから

WordPress（世界中のブログ・企業サイト）、ECサイト構築サービス、ゲームの管理画面やAPI、レンタルサーバーなど、PHPで動いているものは非常に多いです。今回の脆弱性は**特定のアプリではなくPHP本体の問題**なので、PHPを使っていれば全部が対象になりました。

### 2. 「ログイン不要」「アプリのコードより前」で攻撃できる

PHP公式のアドバイザリによると、Apache の mod_php 構成では、**アプリのコードが動く前の段階で、ログインしていない攻撃者のリクエストだけでコード実行に至る攻撃が確認済み**です。PHP-FPM、php-cgi、FrankenPHP、LiteSpeed も対象です。

仕組みをざっくり言うと次のとおりです。

| CVE | 中身（PHP公式の説明を要約） |
| --- | --- |
| CVE-2026-109618（OOMによる破損） | メモリ不足のエラー処理で、リクエストの内部データが**中途半端に初期化された状態**で処理が中断され、後片付けのときにそれを正しいデータとして使ってしまう |
| CVE-2026-109619（古いグローバル状態） | **解放済みのメモリを指したままの内部状態**が残り、同じワーカーが処理する次のリクエストがそれを使ってしまう |

既定で有効な **Session Upload Progress 機能**（ファイルアップロードの進捗を記録する機能）が、確認済みの攻撃の入口の一つです（GMO Flatt Security、OX Security）。設定を変えていない多くのサーバーが、そのまま対象になります。

### 3. 修正前から攻撃が始まっていた

情報が予定より早く漏れたため、PHP公式は公開を1日前倒ししました。それでも、Patchstack や Cloudflare は**修正版の公開前に攻撃の試行を確認**したと報じられています（SecurityWeek）。「修正版が出るまで、外から触れない状態にしておく」のが一番確実なので、各社はサービス停止を選びました。

### 4. 更新したら「確認してから」再開する

PHPを上げると、アプリが動かなくなることがあります。各社は「更新 → 動作確認 → 侵入の痕跡がないか確認 → 再開」という手順を踏むため、**再開時刻はサービスごとにバラバラ**です。

> **推測**: 再開が遅れているサービスは、PHP 8.1以前の古いバージョンを使っていて、公式の修正版にそのまま上げられない（アプリの改修が必要）ケースが含まれていると考えられます。OX Security は、インターネットに公開されたPHPサーバーの約69%が公式修正のない古いバージョンだと推定しています（同社の推計値で、公式の統計ではありません）。

## 利用者向け: やること・やらなくていいこと

### やること

1. **再開は公式で確認する**: 公式サイト・公式X・アプリ内のお知らせを見ます。まとめサイトやSNSの「◯時に復旧」は推測のことがあります。
2. **パスワードの使い回しをやめる**: 現時点で、ドコモ・ニコニコ・グラファーなどは**不正アクセスや情報漏えいは確認されていない**としています。ただ、念のため、複数サービスで同じパスワードを使っているなら変えておくと安心です。二段階認証が使えるサービスでは有効にしておきましょう。
3. **「メンテ明けのお詫び」メールのリンクを不用意に踏まない**: 大きな障害のあとは、便乗したフィッシングが増える傾向があります（**推測**: 今回の便乗フィッシングは、現時点では確認していません）。ログインはブックマークや公式アプリから行います。

### やらなくていいこと

- **ルーターの再起動、回線の解約・乗り換え**: 回線の障害ではありません。
- **アプリの再インストール**: サーバー側のメンテなので、入れ直しても変わりません。データが消えるおそれがあり、逆効果です。
- **「23時以降にネットが遮断される」などの噂を信じる**: SNSで広がった噂で、事実ではありません（Yahoo!リアルタイム検索のまとめでも「噂」とされています）。

## エンジニア向け: 今日やること（PHPを運用している場合）

自社でPHPを動かしているなら、**今日中に**次の手順を進めます。PHP公式は「更新だけが完全な解決策で、設定による回避は危険を下げるだけ」と明言しています。

### 手順1: PHPが動いている場所を洗い出す

見落としやすいのは次のような場所です（Huntress の推奨より）。

- 自社のWebサーバー、コンテナイメージ（`FROM php:8.x-...` のタグ）
- レンタルサーバー・マネージドサービス（事業者の対応状況を確認）
- **ベンダー製品に同梱されたPHP**（管理画面付きの業務パッケージ、cPanel / Plesk など）
- WordPress / Drupal / Joomla / Magento などのCMS
- 開発・検証用で、外部公開されたままのサーバー

### 手順2: バージョンを確認する

```bash
php -v
# PHP-FPM は CLI と別バイナリのことがある（Debian/Ubuntu系の例）
php-fpm8.3 -v
```

修正版は次のとおりです。

| ブランチ | 修正版（これ以上ならOK） | 備考 |
| --- | --- | --- |
| 8.5 | 8.5.12 | |
| 8.4 | 8.4.27 | |
| 8.3 | 8.3.36 | |
| 8.2 | 8.2.35 | **2026年12月31日でサポート終了** |
| 8.1以前 | **公式の修正なし** | ディストリビューション / LTSベンダーのバックポートを確認するか、8.2以上へ移行 |

> 注意: Ubuntu や RHEL など**ディストリビューションのパッケージ**は、バージョン番号を上げずに修正だけを取り込む（バックポート）ことがあります。その場合は `php -v` の数字だけでは判断できません。各ディストリビューションのセキュリティ情報で、修正済みパッケージのバージョンを確認してください。

確認用の小さなスクリプトです（このコンテナの PHP 8.3.6 で動作確認済み。**Web公開ディレクトリには置かず**、CLIで実行してください）。

```php
<?php
// check-php2shell.php : php check-php2shell.php で実行
$fixed = ['8.5' => '8.5.12', '8.4' => '8.4.27', '8.3' => '8.3.36', '8.2' => '8.2.35'];
$branch = PHP_MAJOR_VERSION . '.' . PHP_MINOR_VERSION;
echo 'PHP ', PHP_VERSION, PHP_EOL;
if (!isset($fixed[$branch])) {
    echo "NG: {$branch} 系は公式修正なし（8.2以上へ移行 or ベンダーのバックポートを確認）", PHP_EOL;
} elseif (version_compare(PHP_VERSION, $fixed[$branch], '<')) {
    echo "NG: {$fixed[$branch]} 以上へ更新が必要", PHP_EOL;
} else {
    echo "OK: 修正版です", PHP_EOL;
}
echo 'session.upload_progress.enabled = ', var_export((bool) ini_get('session.upload_progress.enabled'), true), PHP_EOL;
echo 'memory_limit = ', ini_get('memory_limit'), PHP_EOL;
echo 'post_max_size = ', ini_get('post_max_size'), PHP_EOL;
```

実行結果の例（未更新の 8.3.6 の場合）:

```
PHP 8.3.6
NG: 8.3.36 以上へ更新が必要
session.upload_progress.enabled = true
memory_limit = -1
post_max_size = 8M
```

> CLI と PHP-FPM では読み込む php.ini が違うことがあります。FPM の設定で確認したい場合は `php -c /etc/php/8.3/fpm/php.ini check-php2shell.php` のように ini を指定します（パスは環境に合わせてください）。

### 手順3: 先にログを保全する

更新・再起動の**前に**、PHPとWebサーバーのログ、設定ファイル、Web公開ディレクトリのファイル一覧を保存しておきます。修正前から攻撃の試行が出ているため、あとで「やられていないか」を確認する材料になります（watchTowr、Huntress の推奨）。

```bash
# 例: ログと設定を日付付きで退避（パスは環境に合わせる）
sudo tar czf /root/php2shell-evidence-$(date +%Y%m%d%H%M).tar.gz \
  /var/log/nginx /var/log/apache2 /var/log/php*-fpm.log /etc/php 2>/dev/null
```

### 手順4: 更新して、ワーカーを再起動する

```bash
# Debian / Ubuntu 系（ディストリビューションのパッケージを使っている場合）
sudo apt update && sudo apt install --only-upgrade 'php8.3*'
sudo systemctl restart php8.3-fpm      # mod_php なら apache2 を再起動

# RHEL / AlmaLinux / Rocky 系
sudo dnf upgrade 'php*'
sudo systemctl restart php-fpm httpd

# Docker（公式イメージ）の場合: タグを修正版に上げて再ビルド・再デプロイ
#   FROM php:8.3.36-fpm
```

**再起動を忘れないでください。** パッケージを更新しても、動いているワーカーは古いままです。

> **remi リポジトリを使っている場合**: PHP公式は「rpms.remirepo.net は本日時点で更新がない」として、ディストリビューションのパッケージへの切り替えか、ソースからのビルドを強く推奨しています。

### 手順5: すぐ更新できない場合の一時しのぎ

アプリの改修が必要で今日中に上げられない場合は、**外部からのアクセスを止める（またはVPN・IP制限の内側に入れる）**のが最優先です。そのうえで、PHP公式が示す緩和策を入れます。**どれも危険を下げるだけで、安全にはなりません。**

```ini
; php.ini または FPM プール設定（ini_set() や .user.ini では効かない）
session.upload_progress.enabled = 0   ; CVE-2026-109619 の確認済み経路を塞ぐ
memory_limit = -1                     ; CVE-2026-109618 向け（php_admin_value 推奨）
post_max_size = 8M                    ; アップロード不要なら 8M、必要なら 32M
upload_max_filesize = 4M              ; post_max_size より小さく
; PHP 8.5 のみ
; fatal_error_backtraces = 0
```

設定後は**すべてのPHPワーカーを再起動**します。`memory_limit = -1` は1リクエストがメモリを使い切れるようになるため、コンテナや cgroup のメモリ上限と組み合わせてください（PHP公式は `RLIMIT_AS` / `RLIMIT_DATA` は使わないよう注意しています）。

### 手順6: 侵入の痕跡を確認する

Huntress が挙げている確認ポイントです。

- `php-fpm` / `httpd` / `apache2` から `sh`・`bash`・`curl`・`wget`・`nc` などが起動されていないか
- `whoami`・`id`・`uname -a` が Web サーバーから実行されていないか
- Web公開ディレクトリに見覚えのない `.php` ファイル（Webシェル）が増えていないか
- cron・ユーザーアカウントが新しく追加されていないか

```bash
# 直近3日で更新された .php を探す（パスは環境に合わせる）
sudo find /var/www -name '*.php' -mtime -3 -ls
# 追加された cron を確認
sudo ls -la /etc/cron.* /var/spool/cron/ 2>/dev/null
```

怪しいものが見つかったら、そのサーバーをネットワークから切り離し、サーバーが持つ権限（クラウドのIAMロール、DBパスワード、APIキー）を**すべて入れ替える**前提で対応します。メモリ経由でパスワードやAPIキーが漏れうると報告されているためです（Wiz、SecurityWeek）。

### 注意: 「チェックツール」「パッチスクリプト」を安易に実行しない

OX Security は、公開直後から**偽のPoCや、バックドア入りの検出スクリプト**が出回っていると警告しています。GitHubやSNSで見つけたスクリプトを本番サーバーで実行するのはやめ、**PHP公式・ディストリビューション公式のパッケージだけ**を使ってください。

## まとめ

- 10月21日夜〜22日朝の「一斉メンテ」は、**PHPの重大脆弱性 php2shell への予防的な対応**です。回線やクラウドの障害ではありません。
- 利用者は**公式の再開告知を待つ**だけで十分です。パスワードの使い回しをやめ、便乗フィッシングに気をつけましょう。
- エンジニアは**修正版への更新とワーカー再起動**が唯一の解決策です。8.1以前を使っているなら、今回をきっかけにサポート中のバージョンへ移行しましょう。
- 「修正版の公開前に止めて、確認してから再開する」という今回の各社の判断は、利用者には不便でも、**情報漏えいを防ぐための正しい判断**だったと言えます。

PHPの基本やバージョン確認の方法は、ポータルの [PHP まとめ](/technology/php/guide/) も参考にしてください。
