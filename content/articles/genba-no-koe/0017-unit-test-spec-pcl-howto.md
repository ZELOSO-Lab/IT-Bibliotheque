# 【単体テスト】単体テスト仕様書（PCL）の書き方。「正常に動作すること」で差し戻された話と、誰がやっても同じ結果になる書き方

## 現場の声

> 初めて単体テスト仕様書（PCL）を任されたとき、先輩のPCLを見よう見まねで書きました。確認項目は「登録ボタン押下で正常に登録されること」、期待結果は「正常に動作すること」。
>
> レビューでは、**「正常って何？　どの画面に何が出て、DBのどの列にどんな値が入れば正常なの？」**と聞かれ、答えられませんでした。さらに、テストを実施する別のメンバーからは「この入力値はどこから持ってくるんですか」「この行、半分OKで半分NGなんですけど、どう付ければいいですか」と質問が続き、結局ほぼ全行を書き直すことになりました。

**結論：PCLは「自分以外の人が、この表だけを見て実施しても、同じOK/NGになる」ように書きます。** そのために、1行ごとに次の4つを具体的に書きます。

1. **前提条件**：どのデータがある状態で
2. **操作・入力**：何を入力して、何をしたら
3. **期待結果**：画面・DB・ファイルが、どうなっていればOKか（具体的な値で）
4. **確認方法**：何を見て判定し、何をエビデンスとして残すか

この記事では、PCLの列構成と、書くときに現場でハマる7つのポイントを紹介します。**どんな観点でテストケースを洗い出すか**は、次回の記事「[【単体テスト】PCLのテストケース観点一覧](https://itbibliotheque.wordpress.com/?name=pcl-test-case-viewpoints)」で扱います。

## そもそもPCLとは

PCL（プログラムチェックリスト）は、単体テストで「何を、どの条件で、どう確認するか」を一覧にしたものです。現場によって「単体テスト仕様書」「UT仕様書」「テスト項目表」とも呼ばれますが、中身はほぼ同じです。

- **入力にするもの**：詳細設計書（画面項目定義、処理詳細、DBアクセス、メッセージ一覧）
- **使う人**：書いた本人だけでなく、別の実施者、レビュー者、後から改修する人
- **残すもの**：実施結果（OK/NG）、実施日・実施者、エビデンス（画面のハードコピー、SQLの結果、ログ）

PCLは「テストをした証拠」でもあります。リリース後に障害が起きたとき、「このケースは確認済みか」を最初に見られるのがPCLです。

## 前提の例

この記事では、次の「受注登録画面」の登録処理を例にします。

- 顧客コード：必須、半角英数字8桁、顧客マスタに存在すること
- 数量：必須、1〜999 の整数
- 登録ボタンを押すと、受注テーブル（`T_ORDER`）に1件 INSERT し、「登録しました。（I0001）」を表示する
- 入力エラーのときは、エラーメッセージを表示し、エラーの項目にフォーカスを移す

## PCLの列構成

まず、1シートの列を決めます。最低限、次の列があれば「誰がやっても同じ結果」にできます。

| 列 | 書く内容 | 例 |
| --- | --- | --- |
| No | 通し番号 | 12 |
| 設計書項番 | 詳細設計書の処理番号・項目番号 | 処理詳細 3-2 |
| 大分類／中分類 | 画面・処理・項目などの区分 | 登録ボタン押下／入力チェック／数量 |
| 確認観点 | 何を確認するケースか（1行で） | 数量の上限値（境界）を受け付けること |
| 前提条件 | テスト前の状態・テストデータ | 顧客マスタに `C0000001` が存在する |
| 操作・入力値 | 具体的な入力値と操作 | 顧客コード `C0000001`、数量 `999` を入力し、登録ボタン押下 |
| 期待結果 | 画面・DB・ファイルの具体的な状態 | 「登録しました。（I0001）」が表示される。`T_ORDER` に QTY=999 の行が1件追加される |
| 確認方法 | 判定に使うもの・エビデンス | 画面ハードコピー、`SELECT` 結果 |
| 結果 | OK／NG／対象外 | OK |
| 実施日／実施者 | 実施した日と人 | 2026/10/17 山田 |
| 不具合No／備考 | NGのときの管理番号など | — |

表紙・集計用に、別シートとして次も用意しておくと、レビューと進捗報告が楽になります。

- **表紙・改訂履歴**：対象プログラム、版数、作成者、レビュー者
- **テスト環境**：OS、DB（接続先）、ビルドのバージョン、ブラウザ
- **テストデータ一覧**：前提条件で使うデータと、投入用SQL
- **集計**：ケース数、消化数、OK/NG数、未消化の理由

## ハマりどころ1：期待結果が「正常に動作すること」

**症状**

レビューで「正常って何？」と聞かれる。実施者によってOKの判断が変わる。

**原因**

期待結果に**判定できる基準が書かれていない**ためです。「正常に」「正しく」「適切に」は、書いた人の頭の中にしか基準がありません。

**対処**

期待結果は、**目で見て、値で比べられる形**で書きます。

| ✕ ダメな書き方 | ○ 判定できる書き方 |
| --- | --- |
| 正常に登録されること | 「登録しました。（I0001）」が表示される。`T_ORDER` に顧客コード `C0000001`・数量 `999` の行が1件追加される |
| エラーになること | 「数量は1〜999で入力してください。（E0102）」が表示され、数量欄にフォーカスがある。`T_ORDER` の件数が変わらない |
| 正しく計算されること | 金額欄に `29,970`（単価30 × 数量999）が表示される |

ポイントは、**画面・DB・ファイル（ログ）のどれで確認するか**を必ず書くことです。画面だけOKで、DBに入っていない、という不具合は珍しくありません。

## ハマりどころ2：1行に確認を詰め込む

**症状**

「顧客コード未入力、数量未入力、数量0のとき、それぞれエラーになること」のような行があり、2つはOK、1つはNG。結果欄に何を付ければいいか分からない。

**原因**

**1行に複数の確認**が入っていると、OK/NGを1つに決められません。NGになったときに、どの条件が原因かも分からなくなります。

**対処**

**1行＝1つの入力パターン＝1つの判定**にします。

| No | 確認観点 | 操作・入力値 | 期待結果 |
| --- | --- | --- | --- |
| 1 | 顧客コード未入力 | 顧客コード空欄、数量 `10` | E0101 を表示、顧客コード欄にフォーカス |
| 2 | 数量未入力 | 顧客コード `C0000001`、数量空欄 | E0102 を表示、数量欄にフォーカス |
| 3 | 数量の下限外 | 顧客コード `C0000001`、数量 `0` | E0102 を表示、数量欄にフォーカス |

行数は増えますが、実施もレビューも速くなります。行数が多いのは悪いことではありません。

## ハマりどころ3：前提条件・テストデータが書かれていない

**症状**

実施者から「この顧客コードはどこにあるんですか」と聞かれる。自分の環境では通ったのに、別の人の環境ではNGになる。

**原因**

テストの結果は、**テスト前のデータの状態**で変わります。「顧客マスタに存在する顧客コード」というケースは、そのデータが入っていなければ実施できません。

**対処**

- 前提条件の列に、**必要なデータを具体的に**書く（例：顧客マスタに `C0000001`（有効）、`C0000009`（削除フラグ=1）が存在する）
- テストデータは「テストデータ一覧」シートにまとめ、**投入用のSQLも一緒に残す**
- テスト前に毎回同じ状態に戻せるようにしておく（DELETE→INSERT のSQLを用意する）

```sql
-- テストデータ投入（受注登録 PCL 用）
DELETE FROM M_CUSTOMER WHERE CUST_CD IN ('C0000001', 'C0000009');
INSERT INTO M_CUSTOMER (CUST_CD, CUST_NAME, DEL_FLG) VALUES ('C0000001', 'テスト顧客A', '0');
INSERT INTO M_CUSTOMER (CUST_CD, CUST_NAME, DEL_FLG) VALUES ('C0000009', 'テスト顧客Z', '1');
COMMIT;
```

## ハマりどころ4：詳細設計書と対応付いていない

**症状**

レビューで「設計書のこの処理はテストしてないよね？」と指摘される。どこまで書けば終わりなのか分からない。

**原因**

思いついた順にケースを書いていくと、**設計書に書いてあるのにテストしていない処理**が出ます。逆に、設計書にない動きを期待結果に書いてしまうこともあります。

**対処**

- PCLに**「設計書項番」の列**を作り、すべての行に詳細設計書の処理番号・項目番号を書く
- 詳細設計書の処理番号を上から順に見て、**PCLに1行も出てこない番号がないか**を確認する（これが網羅性のチェックになります）
- 設計書に書かれていない動きに気づいたら、PCLに勝手に書かずに、**設計書の修正**として上げる

詳細設計書の側に処理番号が振られていないと、この対応付けができません。詳細設計書の書き方は「[【詳細設計】詳細設計書の書き方](https://itbibliotheque.wordpress.com/?name=detailed-design-doc-howto)」で紹介しています。

## ハマりどころ5：ソースコードを見ながら書く

**症状**

テストは全件OKだったのに、結合テストで「仕様と違う」と指摘される。

**原因**

自分で書いたコードを見ながらPCLを作ると、**コードの動きをそのまま期待結果にしてしまいます**。たとえば、数量チェックを `qty < 999` と書き間違えていても、コードを見て「1〜998がOK」と期待結果を書けば、テストは全部OKになります。バグごと「正しい」と確認してしまうのです。

**対処**

- PCLは**詳細設計書から書く**。コードは見ない
- できれば**コードを書く前に**PCLを作る（設計書の読み違いにも早く気づけます）
- 期待結果の値（メッセージID、計算結果）は、設計書・メッセージ一覧から写す

## ハマりどころ6：確認方法・エビデンスが決まっていない

**症状**

テスト後に「エビデンスを出して」と言われ、何も残っていない。または、全ケースの画面を撮っていて、どれがどのケースか分からない。

**原因**

**何を残せば「確認した証拠」になるか**を、事前に決めていないためです。

**対処**

- 確認方法の列に、**判定に使うもの**を書く（画面、DB、ログ、出力ファイル）
- エビデンスは**ケースNoと紐づける**（ファイル名を `PCL_012_画面.png`、Excelならシート名を `No012` にする）
- DBの確認は、**実行したSQLと結果を両方**残す（どの条件で見たかが分かるように）

```sql
-- No.012 の確認SQL
SELECT ORDER_NO, CUST_CD, QTY, INS_DATE
  FROM T_ORDER
 WHERE CUST_CD = 'C0000001'
 ORDER BY ORDER_NO DESC;
```

エビデンスの粒度（全件か、代表ケースだけか）はプロジェクトで決まっていることが多いので、**書き始める前にリーダーに確認**しておくと手戻りがありません。

## ハマりどころ7：NGになった行を書き換える

**症状**

NGが出たので、コードを直して再実施し、結果欄を「OK」に上書きした。後から「不具合は何件出た？」と聞かれて答えられない。

**原因**

PCLの結果は**品質の記録**でもあります。NGを上書きすると、不具合が出た事実と、直したことを確認した事実が両方消えます。

**対処**

- NGの行は、結果を「NG」のまま残し、**不具合No**（不具合管理表の番号）を書く
- 修正後の再テストは、**再テスト日・再テスト結果の列**に書く（または行を追加する）
- 期待結果自体が間違っていた場合（PCLのミス）は、**PCLの改訂履歴**に残してから直す

| No | 結果 | 実施日 | 不具合No | 再テスト結果 | 再テスト日 |
| --- | --- | --- | --- | --- | --- |
| 12 | NG | 10/15 | BUG-031 | OK | 10/16 |

## PCLを書く手順（まとめ）

### 1. 詳細設計書を読み、処理番号の一覧を作る

- 画面項目定義、処理詳細、DBアクセス、メッセージ一覧を確認する
- 分からない仕様は、PCLを書く前に設計者に確認する

### 2. 列構成とシートを用意する

- No／設計書項番／分類／確認観点／前提条件／操作・入力値／期待結果／確認方法／結果／実施日／実施者／不具合No
- 表紙・テスト環境・テストデータ一覧・集計のシート

### 3. 観点ごとにケースを洗い出す

- 正常系だけでなく、境界値・未入力・異常系・DB・画面操作の観点で洗い出す（詳細は次回の記事）

### 4. 1行ずつ、具体的に書く

- 1行＝1判定。期待結果は値で書き、画面・DB・ログのどれで確認するかを書く

### 5. 設計書項番で網羅性を確認し、レビューを受ける

- PCLに出てこない処理番号がないかを確認してから、レビューに出す

### 6. 実施し、結果とエビデンスを残す

- NGは上書きしない。不具合Noと再テスト結果を残す

## チェックリスト

- [ ] 期待結果に「正常に」「正しく」「適切に」が残っていない
- [ ] 期待結果に、画面・DB・ログのどれで確認するかが書いてある
- [ ] 1行に複数の入力パターンが入っていない
- [ ] 前提条件のデータが具体的に書いてあり、投入用SQLがある
- [ ] すべての行に詳細設計書の項番がある
- [ ] 詳細設計書の処理番号で、PCLに出てこないものがない
- [ ] 期待結果を、ソースコードではなく設計書から書いた
- [ ] エビデンスのファイル名・シート名がケースNoと対応している
- [ ] NGの行を上書きせず、不具合Noと再テスト結果を残している

## まとめ

- PCLは「**自分以外の人が実施しても、同じOK/NGになる**」ことがゴールです。
- そのために、**前提条件・操作と入力値・期待結果・確認方法**を、1行ずつ具体的に書きます。
- **1行＝1判定**、**設計書項番で網羅性を確認**、**コードではなく設計書から書く**。この3つを守るだけで、レビューの差し戻しは大きく減ります。
