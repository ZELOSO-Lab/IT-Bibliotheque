# 【単体テスト】PCLのテストケース観点一覧。正常系だけでレビューに落ちた話と、漏れなく洗い出す10の観点

## 現場の声

> 受注登録画面のPCLを書いて、レビューに出しました。正しい顧客コードと数量を入れて登録できること、を中心に20ケースほど。
>
> レビューでは、**「数量の999は試した？　1000は？」「顧客コードに全角を入れたら？」「登録ボタンを連打したら2件入らない？」「削除済みの顧客は？」**と次々に指摘され、ケース数は最終的に80を超えました。
>
> 実際、結合テストで出た不具合のうち1件は、**数量999がエラーになる**というものでした。チェックの条件が `qty < 999` になっていたのです。境界値を1行書いていれば、単体テストで見つかっていました。

**結論：テストケースは「思いつき」で書くと必ず漏れます。観点の一覧を先に用意し、項目・処理ごとに機械的に当てはめて洗い出します。**

基本になるのは次の3つの考え方です。

1. **同値分割**：同じ結果になる入力をグループに分け、各グループから代表値を1つ選ぶ
2. **境界値分析**：グループの境目（上限・下限とその隣）を必ず試す
3. **デシジョンテーブル**：条件の組み合わせを表にして、漏れなく試す

この記事では、この3つの使い方と、現場で漏れやすい10の観点を紹介します。PCLの列構成や期待結果の書き方は、前回の記事「[【単体テスト】単体テスト仕様書（PCL）の書き方](https://itbibliotheque.wordpress.com/?name=unit-test-spec-pcl-howto)」を参照してください。

## 前提の例

前回と同じ「受注登録画面」を例にします。

- 顧客コード：必須、半角英数字8桁、顧客マスタに存在し、削除されていないこと
- 数量：必須、1〜999 の整数
- 登録ボタンを押すと、受注テーブル（`T_ORDER`）に1件 INSERT し、「登録しました。（I0001）」を表示する

## 基本1：同値分割（グループの代表を1つずつ）

入力値を「同じ結果になるもの」ごとにグループ（同値クラス）に分けます。**OKになるグループ（有効同値）とNGになるグループ（無効同値）の両方**から、代表値を1つずつ選びます。

数量（1〜999）の場合は次のようになります。

| グループ | 範囲 | 代表値 | 期待結果 |
| --- | --- | --- | --- |
| 有効 | 1〜999 | 500 | 登録される |
| 無効（下限より小さい） | 0以下 | -5 | E0102 |
| 無効（上限より大きい） | 1000以上 | 2000 | E0102 |
| 無効（数値でない） | 文字・記号 | `abc` | E0102 |
| 無効（未入力） | 空欄 | （空） | E0102 |

「1〜999 の全部の値を試す」必要はありません。同じグループの中なら、どの値でも結果は同じはずだからです。

## 基本2：境界値分析（境目とその隣を必ず）

不具合は**グループの境目**に集中します。`<` と `<=` の書き間違い、`>` と `>=` の取り違えは、境目の値でしか見つかりません。

数量（1〜999）なら、境界値は次の4つです。

| 値 | 意味 | 期待結果 |
| --- | --- | --- |
| 0 | 下限の1つ下 | E0102 |
| 1 | 下限 | 登録される |
| 999 | 上限 | 登録される |
| 1000 | 上限の1つ上 | E0102 |

冒頭の不具合を、C言語で再現するとこうなります。

```c
/* 数量チェック：1〜999 ならOK（1）、それ以外はNG（0） */
int check_qty(int qty)
{
    if (qty > 0 && qty < 999) {   /* ← 本当は qty <= 999 */
        return 1;
    }
    return 0;
}
```

境界値を含めて実行した結果です。

```text
qty=   -1 -> NG
qty=    0 -> NG
qty=    1 -> OK
qty=  500 -> OK
qty=  998 -> OK
qty=  999 -> NG     ← 上限なのにNG。境界値でだけ見つかる
qty= 1000 -> NG
```

代表値の 500 だけ試していたら、この不具合はOKで通ってしまいます。**数値だけでなく、文字数（8桁の顧客コードなら7桁・8桁・9桁）、日付（期間の開始日・終了日）、件数（0件・1件・上限件数）**にも境界値があります。

## 基本3：デシジョンテーブル（条件の組み合わせ）

条件が複数あり、その組み合わせで結果が変わる処理は、表にしてから洗い出します。

たとえば「顧客ランクが `A` かつ数量が100以上なら10%引き、ランク `A` で100未満なら5%引き、ランク `A` 以外は割引なし」という仕様なら、次の表になります。

| 条件／ケース | 1 | 2 | 3 | 4 |
| --- | --- | --- | --- | --- |
| 顧客ランクが A | Y | Y | N | N |
| 数量が100以上 | Y | N | Y | N |
| **割引率** | **10%** | **5%** | **0%** | **0%** |

条件が2つなら4通り、3つなら8通りです。表にすると、「ランクA以外で100以上」のような**仕様書に書かれていない組み合わせ**にも気づけます。気づいたら、設計者に確認します。

境界値と組み合わせると、ケース2・ケース1の境目として「数量99」「数量100」の2行が加わります。

## 漏れやすい10の観点

ここからは、項目・処理ごとに当てはめる観点の一覧です。PCLを書く前に、この表をコピーして項目ごとに「該当あり／なし」を付けていくと、漏れが減ります。

### 観点1：必須・未入力

- 空欄
- **スペースだけ**（半角スペース、全角スペース）
- 前後にスペースがある値（`" C0000001 "`）を、トリムするのか、エラーにするのか

スペースだけの入力は、画面では「入力あり」、DBでは空文字や NULL になるなど、扱いがぶれやすいところです。

### 観点2：桁数・文字数

- 最大桁ちょうど、最大桁+1
- 最小桁ちょうど、最小桁-1（固定長のコードなど）
- **全角文字の桁数**：画面の「10文字」と、DBの `VARCHAR2(10)`（バイト数）が一致しているか。全角は文字コードによって2〜3バイトになります

### 観点3：文字種

- 半角英数字のみの項目に、全角数字（`１２３`）、半角カナ、記号を入れる
- `'`（シングルクォート）、`"`、`%`、`_`、`\`：SQLの組み立てや LIKE 検索で事故が起きやすい文字
- **機種依存文字・外字**、絵文字（サロゲートペア）：帳票やCSV出力で文字化けしやすい
- 改行・タブ（テキストエリアやCSV取り込み）

### 観点4：数値

- 0、マイナス、小数（`1.5`）、指数表記（`1e3`）
- 先頭ゼロ（`007`）、カンマ付き（`1,000`）
- 計算結果の**桁あふれ**（数量×単価が型の上限を超えないか）
- 端数処理（切り捨て・四捨五入・切り上げ）と、その境目（`x.5`）

### 観点5：日付・時刻

- うるう年の2月29日、うるう年でない年の2月29日（存在しない日付）
- 月末（30日・31日）、**年末年始・年度またぎ**（3月31日→4月1日）
- 0時ちょうど、23時59分59秒（「当日分」の集計で境目になる）
- 開始日 ＞ 終了日（期間の逆転）

### 観点6：処理の分岐

- 設計書の**すべての分岐（if／case）の両方向**を、少なくとも1回ずつ通す（C1網羅）
- ループの 0回・1回・複数回
- 条件の組み合わせは、デシジョンテーブルで確認する

### 観点7：DB・データの状態

- 検索結果が **0件・1件・複数件**、上限件数ちょうど・超え
- キーが存在しない、**論理削除済み**（削除フラグ=1）、有効期限切れ
- 一意制約違反（同じキーで2回登録）
- 登録・更新した**すべての列**の値（登録日時、更新者、バージョン番号などの共通列も）
- エラー時に**ロールバック**され、途中までの更新が残っていないか

### 観点8：画面操作

- 初期表示（初期値、活性・非活性、フォーカス位置）
- **ボタンの連打・二度押し**で、2件登録されないか
- Tab キーの移動順、Enter キーの動き
- 戻る・再表示・ブラウザの更新（Webの場合）
- エラー後に、入力した値が消えずに残っているか

### 観点9：異常系・例外

- DB接続エラー、タイムアウト、デッドロック
- 入力ファイルがない、空、読み取り権限がない、別プロセスが使用中
- 出力先のディスク容量不足、同名ファイルが存在する
- 例外が起きたときに、**決められたメッセージ・ログ・戻り値**になるか

単体テストでは発生させにくいものもあります。その場合は「テーブル名を一時的に変える」「ファイルを読み取り専用にする」など、**発生させる手順も前提条件に書いておきます**。

### 観点10：出力・メッセージ

- メッセージの文言・IDが、メッセージ一覧と一字一句同じか
- ログの出力内容（開始・終了・エラー時）と、出力レベル
- 出力ファイルの文字コード、改行コード、区切り文字、ヘッダ行の有無
- 帳票の改ページ、最終ページ、明細0件のとき

## 観点の当てはめ方（手順）

### 1. 詳細設計書から「項目」と「処理」を書き出す

- 画面項目定義の各項目、処理詳細の各処理番号を一覧にする

### 2. 項目ごとに観点1〜5を当てはめる

- 同値分割で代表値、境界値分析で境目の値を決める
- 該当しない観点は「対象外」と書いておく（検討したことが分かるように）

### 3. 処理ごとに観点6〜10を当てはめる

- 分岐はデシジョンテーブルにする
- DBの状態は「0件・1件・複数件・削除済み」をまず考える

### 4. ケース数を見て、偏りを確認する

- 正常系と異常系の比率が極端でないか（正常系ばかりになっていないか）
- プロジェクトに「1KSあたりのケース数」の目安があれば、それと比べる

### 5. 仕様が書かれていない組み合わせは、設計者に確認する

- PCLの備考に「確認中」と書き、勝手に期待結果を決めない

## チェックリスト

- [ ] 数値・桁数・件数・日付の項目に、境界値（境目とその隣）のケースがある
- [ ] 有効なグループだけでなく、無効なグループの代表値もある
- [ ] 未入力に加えて、スペースだけの入力を試している
- [ ] 全角・記号・`'` を入力するケースがある
- [ ] 条件の組み合わせがある処理は、デシジョンテーブルで洗い出した
- [ ] すべての分岐を、両方向とも1回は通す
- [ ] DBの0件・1件・複数件・削除済みのケースがある
- [ ] ボタンの二度押しで重複登録されないことを確認する
- [ ] エラー時にロールバックされ、更新が残らないことを確認する
- [ ] メッセージの文言・IDを、メッセージ一覧と突き合わせる

## まとめ

- テストケースは、**観点の一覧を当てはめて機械的に洗い出す**と漏れません。
- 基本は**同値分割**（グループの代表値）と**境界値分析**（境目とその隣）。`<` と `<=` の書き間違いは、境界値でしか見つかりません。
- 条件の組み合わせは**デシジョンテーブル**にすると、仕様の抜けにも気づけます。
- 正常系だけでは、PCLの半分も書けていません。**未入力・文字種・DBの状態・二度押し・異常系**を、毎回同じ一覧で確認しましょう。

PCLの元になる詳細設計書の書き方は、「[【詳細設計】詳細設計書の書き方](https://itbibliotheque.wordpress.com/?name=detailed-design-doc-howto)」で紹介しています。
