# 【詳細設計】詳細設計書の書き方。「これではコードが書けない」と言われた話と、PGが迷わない7つのポイント

## 現場の声

> 基本設計書をもとに、初めて詳細設計書を書きました。「登録ボタン押下時、入力チェックを行い、問題なければ受注情報を登録する」。基本設計書の内容を、自分なりに丁寧に書いたつもりでした。
>
> ところが、実装を担当するプログラマからは**「入力チェックって、どの項目をどの順番で？　エラーが2つあったらどっちを出すんですか？　登録する列の値はどこから取るんですか？」**と質問が30件以上。
>
> 次の案件では逆に、ほぼソースコードを日本語にしたような設計書を書いてしまい、今度はレビュー者から「長すぎて仕様が読み取れない。何をしたい処理なの？」と言われました。

**結論：詳細設計書は「この通りに作れば、誰が作っても同じ動きになる」ことがゴールです。** ただし、ソースコードの日本語訳ではありません。書くのは次の3つです。

1. **何を**：入力・出力・使うデータ（項目、型、桁、テーブル、列）
2. **どの順番で**：番号付きの処理手順
3. **どの条件で、どうなるか**：分岐、エラー時の動き、メッセージ

変数名やループの書き方など、「どう書くか」はプログラマに任せます。この記事では、詳細設計書の構成と、書くときに現場でハマる7つのポイントを紹介します。

## 基本設計と詳細設計の違い

| | 基本設計書 | 詳細設計書 |
| --- | --- | --- |
| 読む人 | お客様、業務担当、設計者 | プログラマ、テスト担当（PCLを書く人） |
| 書くこと | **何ができるか**（機能、画面、帳票、業務の流れ） | **どう動くか**（処理の順番、条件、データの扱い） |
| 粒度 | 画面・機能単位 | 項目・処理ステップ単位 |
| 例 | 受注を登録できる | 顧客コード→数量の順にチェックし、最初のエラーで中断。`T_ORDER` に以下の値で INSERT する |

基本設計書が「外から見た動き（外部設計）」、詳細設計書が「中の作り（内部設計）」と呼ばれることもあります。

## 詳細設計書の構成

現場やプロジェクトのテンプレートがあれば、それに従います。ない場合は、次の構成にしておくと、プログラマもテスト担当も迷いません。

| 章 | 内容 |
| --- | --- |
| 1. 表紙・改訂履歴 | 対象機能、版数、作成者、レビュー者、変更内容 |
| 2. 概要 | 目的、基本設計書の該当箇所、処理の全体像（入力→処理→出力） |
| 3. モジュール構成 | 画面・クラス・関数・SQL の一覧と、呼び出し関係 |
| 4. 画面項目定義 | 項目ごとの物理名・型・桁・必須・初期値・入力チェック・エラーメッセージ |
| 5. 処理詳細 | イベント（初期表示、ボタン押下など）ごとの番号付き手順 |
| 6. DBアクセス | テーブル、CRUD、検索条件、ソート順、ロック、トランザクション |
| 7. メッセージ一覧 | メッセージID、文言、種別（情報・警告・エラー） |
| 8. エラー処理 | 例外ごとの動き（メッセージ、ログ、ロールバック、戻り値） |
| 9. 補足 | 共通部品の利用、未決事項、前提・制約 |

## 前提の例

前回までのPCLの記事（「[単体テスト仕様書（PCL）の書き方](https://itbibliotheque.wordpress.com/?name=unit-test-spec-pcl-howto)」「[PCLのテストケース観点一覧](https://itbibliotheque.wordpress.com/?name=pcl-test-case-viewpoints)」）と同じ、「受注登録画面」の登録処理を例にします。基本設計書には、次のように書かれているとします。

> 顧客コードと数量を入力し、登録ボタンを押すと受注が登録される。顧客コードは顧客マスタに存在するものに限る。数量は1〜999とする。

## ハマりどころ1：基本設計書を言い換えただけになっている

**症状**

プログラマから「どの順番で？」「エラーが複数あったら？」と質問が大量に来る。

**原因**

「入力チェックを行い、問題なければ登録する」は、**何をするか（What）**しか書いていません。プログラマが決めなければいけないことが多すぎて、人によって作りが変わります。

**対処**

処理を**番号付きの手順**に分解し、1つの手順に1つの動作を書きます。

```text
【処理5-2】登録ボタン押下

 (1) 入力チェック
   (1-1) 顧客コードが未入力の場合、E0101 を表示し、顧客コード欄にフォーカスを移して処理を終了する
   (1-2) 顧客コードが半角英数字8桁でない場合、E0103 を表示し、顧客コード欄にフォーカスを移して処理を終了する
   (1-3) 数量が未入力、整数でない、または 1〜999 の範囲外の場合、E0102 を表示し、
         数量欄にフォーカスを移して処理を終了する
 (2) 顧客存在チェック
   (2-1) 【SQL-01】で顧客マスタを検索する
   (2-2) 0件の場合、E0104 を表示し、顧客コード欄にフォーカスを移して処理を終了する
 (3) 受注登録
   (3-1) 受注番号を【SQL-02】（シーケンス）で採番する
   (3-2) 【SQL-03】で受注テーブルに登録する（設定値は「6. DBアクセス」の項目対応表のとおり）
   (3-3) コミットする
 (4) 完了処理
   (4-1) I0001 を表示する
   (4-2) 入力欄をクリアし、顧客コード欄にフォーカスを移す
```

「エラーが複数あったら？」の答えは、この手順そのものです（**上から順にチェックし、最初のエラーで終了**）。チェックの順番も仕様なので、設計書に書きます。

## ハマりどころ2：ソースコードの日本語訳になっている

**症状**

設計書が長すぎて、レビュー者が仕様を読み取れない。コードを少し直すたびに設計書も直す必要があり、すぐに古くなる。

**原因**

「変数 `wkQty` に数量テキストボックスの値を `Integer.Parse` して格納する。`For i = 0 To ...`」のように、**実装の書き方**まで書いているためです。

**対処**

詳細設計書に書くのは、**外から確認できる動き**と、**データの扱い**までにします。

| 書く | 書かない（プログラマに任せる） |
| --- | --- |
| チェックの順番と条件、エラー時の動き | 変数名、ローカル変数の型 |
| 使うテーブル・列・検索条件・ソート順 | ループや if の書き方 |
| 計算式と端数処理（例：金額＝単価×数量、円未満切り捨て） | 計算の途中経過の持ち方 |
| 呼び出す共通部品と、その引数・戻り値の意味 | 内部のヘルパー関数の分け方 |

目安は、「**PCLの期待結果に書けるかどうか**」です。テストで確認できない内容は、設計書ではなくコードのコメントに書きます。

## ハマりどころ3：「適切に」「など」「必要に応じて」が残っている

**症状**

プログラマとレビュー者で解釈が分かれる。テスト担当がPCLの期待結果を書けない。

**原因**

曖昧な言葉は、**判断をプログラマに押し付けている**のと同じです。

**対処**

レビューに出す前に、次の言葉で検索して、すべて具体的に書き直します。

| ✕ 曖昧な書き方 | ○ 具体的な書き方 |
| --- | --- |
| 入力値を適切にチェックする | 顧客コードは半角英数字8桁、数量は1〜999の整数であることをチェックする |
| 記号などは入力不可とする | 入力可能文字は `A-Z` `a-z` `0-9` のみとする |
| 必要に応じてログを出力する | エラー時に、ERROR レベルでメッセージIDと顧客コードをログに出力する |
| 大量データの場合は考慮する | 検索結果が1,000件を超える場合、E0201 を表示して検索を中断する |

検索する言葉の例：「適切」「適宜」「など」「等」「必要に応じて」「正しく」「考慮する」「〜とか」

## ハマりどころ4：エラー時の動きが書かれていない

**症状**

正常系は設計どおりに動くのに、エラーが起きたときの動きがプログラマごとにばらばら。DBエラーで画面が固まる、途中までデータが登録される。

**原因**

正常系の手順だけ書いて、**エラーになったら何をするか**を書いていないためです。

**対処**

エラーごとに、次の4つを決めて書きます。

1. **メッセージ**：どのメッセージIDを、どこに表示するか
2. **画面の状態**：入力値を残すか、フォーカスをどこに移すか
3. **データ**：ロールバックするか、途中までの更新をどう扱うか
4. **ログ**：何を、どのレベルで出力するか

```text
【エラー処理】
 ・(3-2) で一意制約違反が発生した場合：ロールバックし、E0105 を表示する。入力値は残す
 ・(2)〜(3) で上記以外のDBエラーが発生した場合：ロールバックし、E9001 を表示する。
   ERROR レベルで SQLCODE とメッセージをログに出力する。入力値は残す
```

## ハマりどころ5：項目の型・桁がDB設計書と合っていない

**症状**

画面では10文字入るのに、登録時にDBエラーになる。プログラムの変数とDBの列の型が合わず、実行時にエラーになる。

**原因**

画面項目定義を基本設計書から写し、**DB設計書（テーブル定義書）と突き合わせていない**ためです。特に、全角文字の桁数（文字数とバイト数）、数値の桁と小数点以下の桁、日付の型でずれが起きます。

**対処**

- 画面項目定義に、**登録先のテーブル・列名と、その型・桁**の列を作る
- DB設計書から、型・桁を**コピーして**貼る（手で打ち直さない）
- 画面の入力桁 ≦ DBの桁 になっているかを、項目ごとに確認する

| 項目名 | 物理名 | 画面の型・桁 | 必須 | 登録先 | DBの型 |
| --- | --- | --- | --- | --- | --- |
| 顧客コード | txtCustCd | 半角英数字 8桁 | ○ | T_ORDER.CUST_CD | VARCHAR2(8) |
| 数量 | txtQty | 整数 3桁 | ○ | T_ORDER.QTY | NUMBER(3) |
| 備考 | txtNote | 全角・半角 50文字 | | T_ORDER.NOTE | VARCHAR2(150) |

型の不一致は、Pro*C の構造体などでは実行時エラーとして出ます。DB設計書から型を写す具体的な手順は「[SELECT結果を構造体にINTOしたらエラー。DB設計書＋VLOOKUP＋サクラエディタで構造体を作り直した手順](https://itbibliotheque.wordpress.com/?name=proc-struct-select-into)」で紹介しています。

## ハマりどころ6：処理番号・SQL番号が振られていない

**症状**

レビューで「3ページ目の真ん中あたりの処理」と言うしかない。PCLから「どの処理のテストか」を指せない。仕様変更のとき、影響範囲が分からない。

**原因**

処理やSQLに**番号（ID）がない**と、設計書の外から参照できません。

**対処**

- 処理詳細の手順に `5-2 (1-3)` のような**階層付きの番号**を振る
- SQL には `SQL-01` のような番号を振り、処理詳細からは番号で参照する
- PCLの「設計書項番」列に、この番号を書いてもらう（網羅性の確認に使えます）

```text
【SQL-01】顧客存在チェック
  SELECT CUST_CD
    FROM M_CUSTOMER
   WHERE CUST_CD = :顧客コード
     AND DEL_FLG = '0'
```

論理削除の条件（`DEL_FLG = '0'`）のように、**検索条件の細部まで書く**のがポイントです。ここが曖昧だと、削除済みの顧客で受注が登録されてしまいます。

## ハマりどころ7：改訂したのに、どこが変わったか分からない

**症状**

仕様変更で設計書を直したが、プログラマが変更箇所に気づかず、古い仕様で実装された。テスト担当もPCLを直していなかった。

**原因**

設計書は**何度も改訂されます**。改訂履歴に「仕様変更対応」としか書いていないと、どこを見直せばいいのか分かりません。

**対処**

- 改訂履歴に、**版数・日付・変更箇所（処理番号）・変更内容・変更理由**を書く
- 本文の変更箇所に**印を付ける**（色を変える、版数を付記する、変更バーを引く）
- 改訂したら、**影響するPCLとプログラムの担当者に連絡する**

| 版 | 日付 | 変更箇所 | 変更内容 | 理由 |
| --- | --- | --- | --- | --- |
| 1.1 | 2026/10/20 | 4. 数量、5-2 (1-3) | 数量の上限を 999 → 9,999 に変更 | お客様要望（課題No.15） |

## 詳細設計書を書く手順（まとめ）

### 1. 基本設計書とDB設計書を読み、不明点を洗い出す

- 基本設計書で決まっていないこと（チェックの順番、エラー時の動きなど）は、書く前に確認する

### 2. モジュール構成を決める

- 画面・クラス・関数・SQL の一覧を作り、呼び出し関係を書く

### 3. 画面項目定義を書く

- DB設計書から型・桁をコピーし、画面とDBの対応を確認する

### 4. 処理詳細を番号付きの手順で書く

- イベントごとに、1手順1動作で書く。分岐とエラー時の動きも書く

### 5. DBアクセス・メッセージ・エラー処理を書く

- SQLに番号を振り、検索条件・ソート順・ロックまで書く

### 6. 曖昧語を検索して潰してから、レビューに出す

- 「適切」「など」「必要に応じて」を検索し、具体的に書き直す

## チェックリスト

- [ ] 処理詳細が、番号付きの手順（1手順1動作）になっている
- [ ] チェックの順番と、エラーが複数あるときの動きが書いてある
- [ ] 変数名やループの書き方など、実装の書き方まで書いていない
- [ ] 「適切」「など」「必要に応じて」「考慮する」が残っていない
- [ ] エラーごとに、メッセージ・画面の状態・ロールバック・ログが書いてある
- [ ] 画面項目の型・桁を、DB設計書と突き合わせた
- [ ] 処理とSQLに番号が振られ、PCLから参照できる
- [ ] 検索条件に、削除フラグや有効期間の条件まで書いてある
- [ ] 改訂履歴に、変更箇所（処理番号）と理由が書いてある

## まとめ

- 詳細設計書のゴールは、「**この通りに作れば、誰が作っても同じ動きになる**」ことです。
- 書くのは「**何を・どの順番で・どの条件でどうなるか**」。ソースコードの日本語訳ではありません。目安は「PCLの期待結果に書けるかどうか」です。
- **番号付きの手順**、**エラー時の動き**、**DB設計書との突き合わせ**、**曖昧語を残さない**。この4つを守ると、プログラマからの質問とレビューの差し戻しが大きく減ります。

詳細設計書ができたら、それをもとにPCLを書きます。書き方は「[【単体テスト】単体テスト仕様書（PCL）の書き方](https://itbibliotheque.wordpress.com/?name=unit-test-spec-pcl-howto)」を参照してください。
