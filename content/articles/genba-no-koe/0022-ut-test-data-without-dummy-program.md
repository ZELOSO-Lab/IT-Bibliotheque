# 【単体テスト】UT用のテストデータ作成、ダミープログラムを書く前に。SQL・Excel・生成AIで時短する5つの方法

## 現場の声

> 「受注登録のUT、テストデータも作っておいてください。一覧画面の確認用に**1万件**、チェック処理の確認用に**境界値と異常系**もお願いします」
>
> 最初に考えたのは、Pro*C でデータ投入用のダミープログラムを書くことでした。ループで INSERT するだけなので簡単だと思っていましたが、コンパイル環境の準備、Makefile、エラー処理、ケースごとの値の切り替え…と見積もると **1〜2日**。しかもUTが終われば捨てるプログラムです。
>
> 先輩に相談すると「それ、SQL 1本で入るよ。境界値はExcelかAIに作らせれば？」。実際にやってみると、**1万件は INSERT 文1本で数秒**、境界値・異常系のデータもケース表から30分ほどで揃いました。

**結論：テストデータは「量はSQLで生成」「ケースはExcelか生成AIでINSERT文を作る」「本物らしさは既存データの流用＋マスキング」で、ほとんどダミープログラムを書かずに作れます。プログラムが必要なのは、固定長ファイルや電文など「DB以外の入力」を作るときくらいです。**

この記事では、作りたいデータの種類ごとに一番速い方法を紹介します。例のSQLは Oracle Database を前提にしています。

## 前提の構成

この記事では、[PCLの書き方](https://itbibliotheque.wordpress.com/?name=unit-test-spec-pcl-howto)や[詳細設計書の書き方](https://itbibliotheque.wordpress.com/?name=detailed-design-doc-howto)と同じ「受注登録画面」を例にします。

| テーブル | 列 | 型 | 備考 |
| --- | --- | --- | --- |
| T_ORDER（受注） | ORDER_NO | VARCHAR2(10) | 主キー |
| | CUST_CD | VARCHAR2(8) | 顧客コード（M_CUSTOMER） |
| | ORDER_DT | DATE | 受注日 |
| | QTY | NUMBER(3) | 数量 1〜999 |
| | NOTE | VARCHAR2(150) | 備考（任意） |
| M_CUSTOMER（顧客） | CUST_CD | VARCHAR2(8) | 主キー |
| | CUST_NM | VARCHAR2(60) | 顧客名 |
| | TEL | VARCHAR2(13) | 電話番号 |
| | DEL_FLG | CHAR(1) | 論理削除 0:有効 1:削除 |

## まず「どんなデータが要るか」で作り方を決める

ダミープログラムを書きたくなるのは、すべてのデータを1つの方法で作ろうとするからです。テストデータは、だいたい次の4種類に分けられます。

| 作りたいデータ | 例 | 一番速い方法 |
| --- | --- | --- |
| **量**（件数が必要） | 一覧の1万件、ページング、性能確認 | 方法1：SQLの連番生成（`CONNECT BY LEVEL`） |
| **ケース**（値のパターンが必要） | 境界値、NULL、削除済みの顧客 | 方法2：Excelの数式でINSERT文を作る／方法3：生成AIに作らせる |
| **本物らしさ**（業務的に整合した値） | 実際の顧客・商品の組み合わせ | 方法4：既存データの流用＋マスキング |
| **期間**（日付ごとに必要） | 月次・半年分の履歴 | [shの日付ループ](https://itbibliotheque.wordpress.com/?name=sh-monthly-test-data) |

1つの画面のUTでも、ほとんどは「量」と「ケース」の組み合わせです。まずテストケース（PCL）を見て、どのケースにどの種類のデータが要るかを分けてから作り始めると、無駄な作業がなくなります。

## 方法1：件数が必要なら、SQLの連番生成で一発

Oracle では `CONNECT BY LEVEL <= N` で、1〜N の連番の行を作れます。これを `INSERT ... SELECT` と組み合わせると、ループを書かずに大量のデータを入れられます。

```sql
-- 顧客 100件（UT00001〜UT00100）
INSERT INTO M_CUSTOMER (CUST_CD, CUST_NM, TEL, DEL_FLG)
SELECT 'UT' || LPAD(LEVEL, 6, '0'),
       'テスト顧客' || LEVEL,
       '090-0000-' || LPAD(LEVEL, 4, '0'),
       '0'
  FROM DUAL
CONNECT BY LEVEL <= 100;

-- 受注 10,000件（顧客100社・受注日31日・数量1〜999に分散）
INSERT INTO T_ORDER (ORDER_NO, CUST_CD, ORDER_DT, QTY, NOTE)
SELECT 'UT' || LPAD(LEVEL, 8, '0'),
       'UT' || LPAD(MOD(LEVEL - 1, 100) + 1, 6, '0'),
       DATE '2026-10-01' + MOD(LEVEL - 1, 31),
       MOD(LEVEL - 1, 999) + 1,
       CASE WHEN MOD(LEVEL, 10) = 0 THEN NULL ELSE '備考' || LEVEL END
  FROM DUAL
CONNECT BY LEVEL <= 10000;

COMMIT;
```

ポイントは次の3つです。

- **値は `MOD` でばらけさせる**：`MOD(LEVEL - 1, 100) + 1` で 1〜100 を繰り返します。顧客・日付・数量を別々の周期で回すと、組み合わせが偏りません。
- **NULL も混ぜる**：`CASE WHEN MOD(LEVEL, 10) = 0 THEN NULL` で10件に1件を NULL にしています。任意項目は NULL のデータがないと、画面の表示崩れを見落とします。
- **テストデータと分かる値にする**：キーの先頭を `UT` にしておくと、後で消すときに条件1つで済みます（後述）。

> **補足：数十万件を超える場合は、分けて入れます。** 1回の INSERT で件数が多すぎると、UNDO 領域や一時表領域が足りなくなることがあります。10万件ずつに分けて `COMMIT` するか、`LEVEL` の範囲を変えて複数回実行してください。また `CONNECT BY LEVEL` は Oracle 独自の書き方です。PostgreSQL なら `generate_series(1, 10000)`、SQL Server なら再帰CTEで同じことができます。

## 方法2：ケースごとの値は、Excelの数式でINSERT文を作る

境界値や異常系のように、**ケースごとに値を決めたいデータ**は、Excel で表を作るのが一番速く、レビューもしやすい方法です。PCL がExcelなら、ケース番号と値をそのまま並べられます。

| | A | B | C | D | E | F |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | ケース | ORDER_NO | CUST_CD | ORDER_DT | QTY | NOTE |
| 2 | 3-1 下限 | UT90000001 | UT000001 | 2026/10/01 | 1 | |
| 3 | 3-2 上限 | UT90000002 | UT000001 | 2026/10/01 | 999 | 備考50文字の確認… |
| 4 | 4-1 削除済み顧客 | UT90000003 | UT000099 | 2026/10/31 | 10 | |

G列に、INSERT 文を作る数式を入れて下にコピーします。

```text
="INSERT INTO T_ORDER (ORDER_NO, CUST_CD, ORDER_DT, QTY, NOTE) VALUES ('"&B2&"', '"&C2&"', DATE '"&TEXT(D2,"yyyy-mm-dd")&"', "&E2&", "&IF(F2="","NULL","'"&SUBSTITUTE(F2,"'","''")&"'")&"); -- "&A2
```

G列をコピーして SQL Developer に貼り付け、`F5`（スクリプトの実行）で流せば完了です。

- **空欄は `NULL` に変換**しています。`''` で入れると Oracle では NULL 扱いになりますが、意図が分かるように明示します。
- **シングルクォートは `SUBSTITUTE` で `''` にエスケープ**しています。備考に `'` を含むケースで SQL が壊れるのを防ぎます。
- **末尾にケース番号をコメントで付けておく**と、実行ログがそのままエビデンスになります。

> **補足：件数が多い場合は SQL*Loader も使えます。** Excel を CSV で保存し、制御ファイルを書いて `sqlldr` で取り込む方法です。数千件以上を何度も入れ直す場合は、INSERT 文より速くなります。
>
> ```text
> -- order.ctl
> LOAD DATA
> CHARACTERSET JA16SJIS
> INFILE 'order.csv'
> APPEND INTO TABLE T_ORDER
> FIELDS TERMINATED BY ',' OPTIONALLY ENCLOSED BY '"'
> TRAILING NULLCOLS
> (ORDER_NO, CUST_CD, ORDER_DT DATE "YYYY/MM/DD", QTY, NOTE)
> ```
>
> ```text
> sqlldr userid=ut_user/password@ORCL control=order.ctl log=order.log
> ```
>
> 1行目に見出しがある場合は `OPTIONS (SKIP=1)` を `LOAD DATA` の前に書きます。Excel から保存した CSV は Shift_JIS になるため、`CHARACTERSET` を合わせないと文字化けします。

## 方法3：境界値・異常系のパターン出しは、生成AIに任せる

「どんな値を入れればいいか」を考える時間がかかるなら、**テーブル定義とテストケースを生成AIに渡して INSERT 文を作らせる**のが速い方法です。値を考える作業と、SQL を書く作業が同時に終わります。

```text
以下のテーブル定義とテストケースに対して、Oracle の INSERT 文を作ってください。

# 条件
- 主キー ORDER_NO は 'UT9' で始まる10桁の連番
- 顧客コードは M_CUSTOMER に存在する 'UT000001'（有効）と 'UT000099'（DEL_FLG='1'）を使う
- 1ケース1文。各文の末尾に「-- ケース番号 ケース名」のコメントを付ける
- DBの制約（型・桁・NOT NULL）に違反する値は INSERT 文にせず、「画面入力で確認するケース」として別に一覧にする

# テーブル定義
（T_ORDER と M_CUSTOMER の CREATE TABLE 文、または DB設計書の表を貼る）

# テストケース
（PCL のケース番号・確認内容・入力値の列を貼る）
```

使うときの注意点は3つです。

- **制約違反のデータは入らない**：数量 `1000` や 9桁の顧客コードは、`NUMBER(3)` や `VARCHAR2(8)` の制約で INSERT 自体がエラーになります。これらは「DBに入れておくデータ」ではなく「画面から入力する値」です。プロンプトで分けるように指示しておくと、エラーで止まる SQL が混ざりません。
- **出てきた値は、PCL と突き合わせて確認する**：AI は境界値の「上限」と「上限＋1」を取り違えることがあります。ケースごとに期待値が合っているかは、自分で確認してください。
- **本番データ・顧客情報は渡さない**：渡すのはテーブル定義とケースだけにします。社内で生成AIの利用ルールがある場合は、それに従ってください。

## 方法4：本物らしいデータは、既存データの流用＋マスキング

業務的に整合したデータ（実在する商品と単価の組み合わせなど）が必要な場合は、ゼロから作るより、**結合テスト環境やマスタ整備済みの環境からコピー**するほうが速く確実です。

```sql
-- 結合環境の顧客をコピーし、個人情報だけ置き換える（DBリンク IT_LINK がある場合）
INSERT INTO M_CUSTOMER (CUST_CD, CUST_NM, TEL, DEL_FLG)
SELECT CUST_CD,
       'テスト顧客' || ROWNUM,
       '090-0000-' || LPAD(ROWNUM, 4, '0'),
       DEL_FLG
  FROM M_CUSTOMER@IT_LINK
 WHERE ROWNUM <= 500;
```

- **個人情報の列は、コピーと同時に置き換える**：名前・電話番号・メールアドレス・住所は、コピーした後ではなく `SELECT` の中で置き換えます。一度でも本物の値がUT環境に入ると、ログやエビデンスに残ってしまいます。
- **DBリンクがない場合**は、元の環境で SQL Developer の「エクスポート」（INSERT 文形式）を使うか、DBA に Data Pump（`expdp` の `QUERY` オプション）での抽出を依頼します。
- **本番環境からのコピーは、必ずプロジェクトのルールを確認する**：本番データのUT利用を禁止している現場は多いです。

## 方法5：「消して作り直せる」ようにしておく

テストデータ作成で意外と時間がかかるのが、**やり直し**です。テストで更新・削除したデータを元に戻すたびに、作り直しが発生します。最初から次の2つを用意しておくと、何度でも数秒で戻せます。

```sql
-- 00_delete.sql：テストデータだけを消す（キーの先頭 'UT' で判定）
DELETE FROM T_ORDER    WHERE ORDER_NO LIKE 'UT%';
DELETE FROM M_CUSTOMER WHERE CUST_CD  LIKE 'UT%';
COMMIT;
```

```sql
-- 99_setup.sql：消して、全部入れ直す（SQL Developer から F5 で実行）
@00_delete.sql
@01_customer.sql
@02_order_bulk.sql
@03_order_cases.sql
```

- **子テーブルから先に消す**：外部キーがある場合、親（M_CUSTOMER）から消すとエラーになります。
- **`TRUNCATE` は使わない**：ほかの人のデータまで消え、ロールバックもできません。共有のUT環境では、自分のデータだけを条件で消します。
- **スクリプトは構成管理（SVN / Git）に入れる**：UT を再実施するとき、別の人が同じデータを再現できます。

## どうしてもプログラムが必要な場合の最短手順

DB ではなく、**固定長ファイル・CSV・電文**など、プログラムが読み込む「入力ファイル」が必要な場合は、生成するスクリプトを書きます。ただし、本番と同じ言語（C や Pro*C）で書く必要はありません。

1. **ファイルレイアウト定義書を生成AIに渡し**、「このレイアウトで N 件のファイルを作る Python スクリプトを書いて」と頼む
2. 出てきたスクリプトで、**1レコードの長さを `assert` で必ずチェックする**
3. 件数を引数にして、少ない件数で中身を確認してから本番の件数で作る

例として、1レコード32バイトの固定長ファイルを作るスクリプトです（コンテナの Python 3 で実行して確認しています）。

```python
# 固定長ファイル（1レコード32バイト）を作る
# レイアウト: 受注番号10 + 顧客コード8 + 受注日8 + 数量3（0埋め） + 予備3
import sys

count = int(sys.argv[1])          # 件数
with open("ORDER.DAT", "w", encoding="ascii", newline="\n") as f:
    for i in range(1, count + 1):
        order_no = f"UT{i:08d}"                 # 10桁
        cust_cd  = f"UT{i % 100:06d}"           # 8桁（100社に分散）
        order_dt = f"202610{i % 28 + 1:02d}"    # 8桁（1〜28日）
        qty      = f"{i % 999 + 1:03d}"         # 3桁（1〜999）
        rec = f"{order_no}{cust_cd}{order_dt}{qty}{'':3}"
        assert len(rec) == 32, rec
        f.write(rec + "\n")
```

```text
$ python3 make_fixed.py 1000
$ head -3 ORDER.DAT
UT00000001UT00000120261002002   
UT00000002UT00000220261003003   
UT00000003UT00000320261004004   
$ awk '{print length($0)}' ORDER.DAT | sort -u
32
```

- **改行コードを合わせる**：Windows 向けなら `newline="\r\n"`、改行なしの固定長なら `"\n"` を付けずに書きます。改行の有無でレコード長が変わり、読み込みでずれます。
- **全角文字を含むレイアウトは、バイト数で数える**：Shift_JIS では全角1文字が2バイトです。`len()` は文字数なので、`len(rec.encode("cp932"))` でチェックします。
- **Python がない環境なら、awk や sh でも作れます**：`awk 'BEGIN{for(i=1;i<=1000;i++) printf "UT%08d...\n", i}'` のように `printf` の書式で0埋めできます。

## 時短の目安

受注登録のUT（1万件＋境界値・異常系20ケース）を例にした目安です。環境やケース数によって変わります。

| 作り方 | 準備 | 作成・投入 | 作り直し |
| --- | --- | --- | --- |
| Pro*C でダミープログラム | 1〜2日（環境・Makefile・エラー処理） | 数分 | 値を変えるたびに修正・再ビルド |
| SQL連番＋Excel／生成AI | 30分〜1時間 | 数秒〜数分 | `99_setup.sql` で数秒 |

## チェックリスト

- [ ] PCL を見て、ケースごとに「量・ケース・本物らしさ・期間」のどれが要るかを分けた
- [ ] 件数が必要なデータは `CONNECT BY LEVEL` ＋ `MOD` で作った
- [ ] 任意項目に NULL のデータを混ぜた
- [ ] 境界値・異常系は Excel か生成AIで INSERT 文を作り、ケース番号をコメントに付けた
- [ ] DB の制約に違反する値は、INSERT せず画面入力のケースに分けた
- [ ] 流用したデータの個人情報は、`SELECT` の中で置き換えた
- [ ] テストデータのキーに目印（`UT` など）を付け、削除スクリプトを用意した
- [ ] セットアップ用のスクリプトを構成管理に入れた

## まとめ

- テストデータは、**量・ケース・本物らしさ・期間**に分けると、それぞれ一番速い作り方が決まります。
- **量は `CONNECT BY LEVEL` の INSERT 文1本**、**ケースは Excel の数式か生成AIで INSERT 文を作る**のが最速です。
- 本物らしいデータは既存環境から流用し、**個人情報はコピーと同時に置き換えます**。
- 最初に**削除と再投入のスクリプト**を作っておくと、UT のやり直しが数秒で済みます。
- プログラムが必要なのは、固定長ファイルや電文などの入力ファイルを作るときです。その場合も、生成AIにレイアウトを渡して Python などで書けば短時間で済みます。

「UTが終われば捨てるプログラム」に1日かけるより、30分で作れて何度でも再現できるSQLとスクリプトを残すほうが、テストの品質も上がります。
